# 第一部分 逐页大纲与讲稿（第 1~27 页）

## 第 1 页 · 封面
- **要点**：项目名《ERP 财务数据契约治理平台》；副标题"给财务数据装一道自动化的安检门"；技术栈一行。
- **配图**：深蓝封面 + 右侧金色"契"字印章卡片（DATA CONTRACT）。
- **讲稿**：各位老师好，我汇报的项目是《ERP 财务数据契约治理平台》。一句话概括：我给财务数据装了一道自动化的「安检门」——脏数据在进入数仓之前就被拦下来，而不是等报表崩了再返工。这个项目从一个最简单的本地数据质检实验做起，经过七个阶段的迭代，最终长成了包含定时调度、质量门禁、钉钉告警、变更治理和 LLM 辅助诊断的完整数据质量工程。全程在 100 万行真实基准数据上验证，最终落地 72 项自动化财务内控检查。我是财务背景半路转码，这个项目也是我「懂业务、会工程」双向能力的证明。接下来按「为什么做、怎么做、做出了什么、效果如何」的主线向各位汇报。

## 第 3 页 · 一个财务人的噩梦：月结崩盘之夜
- **要点**：报表金额 999999999、空值率 0.5%→40%、币种乱码；根因三类（上游 ERP 升级改字段/第三方推送格式突变/录入异常）；传统治理四大致命问题：发现太晚、定位太难、责任不清、修复靠人；死循环一句话。
- **配图**：顶部红色事故卡 + 四个编号痛点卡 + 底部死循环文字链。
- **讲稿**：先看这个项目要解决的真问题。我是财务出身，这个场景我太熟悉了：月末关账前一晚，BI 报表突然崩了——某张报表金额变成一串 9，另一张表空值率从千分之五飙到百分之四十，还有一批交易的币种直接成了乱码。事后排查，根因无非三种：上游 ERP 升级悄悄改了字段逻辑、第三方系统推送格式突变、或者业务员录入了异常金额。但等财务在报表上看到时，脏数据早就进了数仓，被各种下游引用，生米煮成熟饭。传统治理方式是一个事后补救的死循环，有四个致命问题：发现太晚、定位太难、责任不清、修复靠人。最痛的是第四点——每次都用临时脚本打补丁，问题没有沉淀成机制，下个月换个姿势再犯一次。这个项目要打破的就是这个循环。

## 第 4 页 · 数据契约：给数据立一份「法律合同」
- **要点**：Data Contract = 生产者与消费者的正式约定；约定字段/类型/必填/唯一/取值范围；声明式 YAML 业务可读；机器可执行——进数仓前逐行扫描、违约熔断告警；规则归业务所有；纳入 Git 可回滚可留痕，满足内控。
- **配图**：左右双卡（合同 / 安检门）+ 底部一句话定位。
- **讲稿**：破局的钥匙叫数据契约，Data Contract。可以把它理解成数据的「法律合同」：数据的生产者和消费者坐下来，把「数据应该长什么样」白纸黑字约定清楚——有哪些字段、什么类型、哪些必填、哪些唯一、取值必须在什么范围内。关键在两点。第一，这份合同不是写在 Word 里给人看的，而是写在一份 YAML 文件里、可以被机器直接执行——数据进数仓之前，引擎拿着合同逐行扫描，违约就熔断告警，脏数据在门口就被拦下。第二，它是声明式的，财务主管、内控经理自己就能读懂、能修改，规则的所有权真正归业务。所以它不是又一个清洗脚本，它是把数据质量标准从程序员的脑子里、从口口相传的口径里，变成一份正式、可执行、可审计的资产。这一条正好命中财务内控对「留痕、可回滚」的硬性要求。

## 第 5 页 · 为什么不直接写个 Python 清洗脚本？
- **要点**：三个本质差别——规则所有权（改 YAML vs 改代码发版）、可读性与解耦（业务可读 vs 随人员失传）、可审计留痕（Git vs 散落各处）。
- **配图**：三行"红（脚本痛点）/绿（契约答案）"对比卡。
- **讲稿**：可能有老师会问：查脏数据，写个 Python 脚本跑一遍不就行了？这是我在设计时认真权衡过的问题——脚本解决的是「功能」，契约解决的是「治理」，三个本质差别。第一，规则所有权：脚本路线下规则埋在代码里，财务想调一个审批阈值，得找程序员改代码、走发版；契约路线下规则是声明式 YAML，业务人员自己改一行就生效。第二，可读性：脚本非技术人员读不懂，口径随着人员流动就失传了；契约里 validValues 中括号 1 2 3 4 这种写法，财务主管一眼就能看懂。第三，可审计：脚本散落在各人电脑里，谁改的、为什么改无从追溯；契约纳入 Git，每次变更可回滚可追责。对财务场景来说，第三点不是加分项，是内控的硬性要求。这就是选契约路线的根本原因。

## 第 6 页 · Shift-Left：把审计「左移」到数据源头
- **要点**：四环节链路（产生→接入→契约门禁→数仓报表），门禁设在进数仓之前；右移代价 vs 左移收益对比。
- **配图**：四节点流程图，第三节点深色高亮为"门禁"；下方红/绿对比卡。
- **讲稿**：数据契约背后是一个更普适的工程思想，叫 Shift-Left，左移。这条链路是数据的一生：ERP 里产生交易，接入落地，进数仓，最后变成报表。传统审计在链条最右端、也就是报表阶段才介入——这时发现问题的成本是最高的，就像产品出厂上市后才发现缺陷，召回返工的代价远大于产线上的质检。左移就是把质检环节往链条左边搬，搬到数据进入数仓之前。本项目在「接入」和「数仓」之间设了一道契约门禁：数据到了先过安检，合格放行，违约熔断告警。左右两边的卡片是两种模式的对比：右移的代价是污染扩散、回刷返工、反复再犯；左移的收益是门口拦截、规则沉淀、成本数量级下降。整个项目后续所有工程化动作——定时调度、告警、治理——都是在把这道门做得更牢、更自动。

## 第 7 页 · 验证数据：100 万行 × 49 列的真实 ERP 基准数据集
- **要点**：Kaggle「Universal ERP Accounting Risk Dataset」；100 万行×49 列；混有 NetSuite/Oracle/D365/QuickBooks 四种 ERP；内存 603.6MB、Parquet 约 600MB；版本 Universal_ERP_Fraud_Benchmark_1.0；选它的三个理由；诚实边界（基准数据较干净→后续异常注入反向验证）。
- **配图**：四个大数字（100 万/49 列/4 种/603.6MB）+ 要点列表。
- **讲稿**：巧妇难为无米之炊，先看验证用的数据。我选的是 Kaggle 上的通用 ERP 会计风险数据集：100 万行、49 列，混有四种主流 ERP 的交易记录，内存占用 603.6 MB，版本号叫反舞弊基准 1.0——本身就是为审计风控场景设计的标准数据集。选它有三个原因：字段语义和真实财务场景一一对应；百万行量级足够验证「全量校验替代人工抽查」；基准数据集让结果可复现、可对比。也要诚实说明边界：基准数据本身比较干净，所以光跑出全绿不足以证明门禁有效——后面业务系统篇我专门设计了异常注入实验，人为埋入五类违规数据，验证门禁能精确把它们抓出来。

## 第 8 页 · 七阶段演进：从一次手动检查到数据质量工程
- **要点**：七阶段箭头图；检查项演进 25→34→55→63→72；主线逻辑（先证明规则有用→再自动跑→再解决数据来源→最后解决契约谁来管）；演进驱动力 = MVP 迭代，缺口由上一阶段验证真实暴露。
- **配图**：七个 V 型箭头（阶段 1-7）+ 数字演进条。
- **讲稿**：先看整个项目的演进地图，七个阶段，一条清晰的主线。阶段一基础篇，在本地把第一份数据契约跑通；阶段二注入七条反舞弊规则并用 Streamlit 搭了看板；阶段三把系统搬进 Docker 和 Kestra，数据迁进 PostgreSQL，实现每天凌晨六点自动门禁；阶段四补上密码管理和钉钉告警；阶段五从零造了一个六表一视图的 ERP 业务系统和造数器；阶段六做了前台页面；阶段七给契约文件本身装上变更治理并引入大模型。注意主线逻辑：先证明规则有用，再让规则自动跑，再解决数据从哪来，最后解决契约谁来管。每个阶段的缺口都是上一阶段验证中真实暴露的，这是典型的 MVP 迭代式工程方法，而不是一开始就画一张宏大蓝图。右下方这条数字线是检查项的演进：25、34、55、63、72，每一级都有明确的增量来源。

## 第 9 页 · 四层架构：业务侧 → 数据侧 → 契约运行时 → 治理层
- **要点**：业务侧（Streamlit 前台：申请→审批→记账）→ 数据侧（erp_demo 六表一视图）→ 契约运行时（72 项 YAML 契约 + datacontract-cli + Kestra 06:00 调度 + 钉钉 + Pytest）→ 治理层（CCR 变更单/Git/影响评估/回退/LLM Copilot）。
- **配图**：四条横向层带自下而上 + 数据流箭头。
- **讲稿**：这是项目最终的总体架构，自下而上四层。最底层是业务侧：一个 Streamlit 实现的 ERP 前台，员工登录、提交申请、领导审批、自动记账——数据由真实业务动作产生。往上是数据侧：PostgreSQL 业务库 erp_demo，六张表加一个视图，最上面的视图 erp_transactions 是契约的接口适配层。第三层是契约运行时：契约文件定义 72 项检查，datacontract-cli 执行，Kestra 每天凌晨六点自动调度，失败触发钉钉告警，另有 Pytest 做回归。最上面是治理层：管理「契约本身的变化」——谁提的变更、为什么改、谁批的、影响哪些历史数据、怎么回退，还有 LLM Copilot 辅助。一句话：业务侧管数据从哪来，数据侧管数据存哪，运行时管数据合不合格，治理层管规则本身合不合规。

## 第 10 页 · 两条独立链路，仅在 JSON 报告处交汇
- **要点**：自动化校验链（Compose→Kestra→临时容器→72 项检查→JSON/钉钉，无人值守）+ 人肉查看链（JSON→Streamlit 看板→浏览器）；解耦设计：JSON 是双方唯一契约。
- **配图**：左右双卡对比 + 底部设计要点。
- **讲稿**：运行机制上，系统由两条独立链路组成，只在 JSON 报告这一个点交汇。左边是自动化校验链，全程无人值守：Docker Compose 拉起 Kestra 和 PostgreSQL，cron 每天凌晨六点触发 Flow，临时创建一个 Python 任务容器执行 72 项检查，结果写成 JSON 报告；失败则 errors 块向钉钉群发告警。右边是人肉查看链，给业务用的：JSON 报告拷回本地，Streamlit 看板渲染，业务人员在浏览器里看指标卡和明细。这个解耦是有意设计的：看板挂了不影响门禁照常跑——JSON 报告是两条链路之间唯一的契约。这本身就是数据契约思想在系统设计上的一次应用。

## 第 11 页 · 技术选型总览
- **要点**：九行选型表：datacontract-cli 1.2.0 / Kestra latest / PostgreSQL 18 / Docker Desktop+WSL2 2.7.14 / Streamlit 1.64.0 / psycopg2 2.9.13 / Pytest 9.1.1 / DeepSeek 20261002，各附入选理由。
- **配图**：全宽表格（组件/选型/版本/理由）。
- **讲稿**：技术选型一览，每一项都有明确理由，不是追热点。契约引擎选 datacontract-cli，因为它是围绕数据契约这个开放标准构建的，YAML 是它的原生语言。调度选 Kestra 而不是 Airflow：开源、Flow 用 YAML 声明、自带 Web 界面，对个人项目上手成本明显更低。数据库选 PostgreSQL 18，它是解决「容器间共享数据」的结构性方案。看板和前台用 Streamlit，纯 Python 就能交付数据网页。驱动用 psycopg2 的 binary 预编译版，避免 Windows 上编译 C 扩展的坑。测试用 Pytest 做全链路回归；LLM 用 DeepSeek 网页对话版，走提示词工程加确定性闸门的路线——为什么不用 API，治理篇会讲。

## 第 12 页 · 一条字段的旅程：从业务动作到契约检查
- **要点**：「缺凭证」字段血缘五步：前台勾选 → business_requests.support_document_flag → journal_entries.supporting_document_flag → 视图反向映射 missing_support_flag = NOT … → 契约红线 SQL 违规=0；反向映射是确定性代码；18 字段来源审计；单据级反查（TXN→REQ→APR→POL→人/项目）。
- **配图**：五节点横向链路图，末节点深色。
- **讲稿**：架构的最后一块拼图是字段血缘——以「缺凭证」这条审计红线为例，看一个字段的完整旅程。第一步，员工在前台提交申请时勾选「是否含支持性凭证」，落在申请表；审批通过自动记账后，进入分录表；再经视图做反向映射——NOT 运算，业务语言的「有凭证」变成审计语言的「缺凭证」；最终契约里的红线规则对视图执行 SQL，查出违规行数必须为零。三个要点：反向映射是确定性代码完成的，不靠人工判断；18 个契约字段每一个都能回答来自哪张表、哪个操作、哪条派生逻辑；支持单据级反查，从任何一个交易号都能倒推出申请、审批、命中的审批策略和当事人。有了这条血缘链，「数据合不合格」才真正变成了「业务合不合规」。

## 第 13 页 · 章节隔页：PART 03 基础篇
- **讲稿**：下面进入主体部分。第三章，基础篇。这个阶段要回答一个最朴素的问题：数据契约这个思想，在真实数据上到底行不行？方法上我坚持一个顺序：先探索数据，再写规则——不看数据就写规则是闭门造车。这个阶段的产出有四个数字：100 万行全量校验、首版契约 34 项检查、全程踩了九个坑并逐一排掉、百万行校验只要 1.42 秒。

## 第 14 页 · 三大数据洞察：规则必须长在证据上
- **要点**：洞察一缺失三梯队（39 字段全非空可 required / invoice_id、approver_id 各缺约 400 条为业务性缺失 / 供应商银行变更域 8 字段空值率 99.97%+ 绝不 required）；洞察二金额分布定防呆线（min -18.96 万 / max ≈271.5 万 / 防呆线 500 万零误报）；洞察三 12 个审计基因标志位；方法论「证据在哪一行」。
- **配图**：三张洞察卡 + 底部方法论。
- **讲稿**：写契约之前先做数据探索，用 pandas 的 info 和 describe 把数据底细摸清，得到三个直接决定规则设计的洞察。洞察一，缺失分三个梯队：39 个字段 100 万行全非空，可以放心设为必填；发票号、审批人号各缺四百来条，占万分之四，这是业务性缺失；而供应商银行账户变更相关的 8 个字段空值率超过 99.97%，如果误设必填，全量数据都会被判违约——可见 required 不是越多越好。洞察二，金额分布：最小值是负的 18.9 万，最大约 271.5 万。据此把防呆线设在 500 万——正常业务永远碰不到，只有系统错误或录入异常才会触发，误报率为零。洞察三，数据集自带 12 个审计风险标志位，它们就是反舞弊规则的现成落点。这三条共同体现一个方法论：每条规则都能追溯到证据的某一行，不拍脑袋。

## 第 15 页 · 首版契约：三层架构 + 8 个核心字段 + 25 项检查
- **要点**：规则层（YAML）/执行层（datacontract-cli 1.2.0）/数据层（Parquet 100 万行）；初版 8 字段表；计数公式：检查项总数 = 字段数×3 + 唯一性（25=8×3+1）；首跑 25 项全绿 6.46 秒。
- **配图**：左侧三层堆叠 + 右侧字段表 + 绿色结果条。
- **讲稿**：契约怎么落地？先看架构，三层：规则层是那份 YAML 契约文件，写「数据应该什么样」；执行层是 datacontract-cli，读契约、连数据、执行检查；数据层就是 100 万行的 Parquet 文件。初版契约只圈了 8 个核心字段，设计思路是「身份 + 业务事实 + 合规风险点」。这里有一个贯穿全项目的方法论：检查项总数是可数、可验证的——字段数乘 3，再加主键唯一性，8 个字段就是 25 项。别小看这个公式，后面每次给契约加规则，我都用这个数字核对「新规则到底生效没有」——它是发现「静默失效」的关键武器，下一页就会讲到。首版跑通：25 项全绿，耗时 6.46 秒。

## 第 16 页 · 契约文件长什么样：业务人员也能读懂的 YAML
- **要点**：YAML 片段（models/fields/quality library 规则）；声明式不是代码；缩进即语法（字段名 6 空格/属性 8/规则项 10）；两类规则（字段级约束自动展开 + library metric）；头信息 dataContractSpecification: 0.9.3 开放标准。

- **讲稿**：看一段真实的契约内容。models 下面是表，fields 下面是字段。transaction_id 声明 string 类型、required 必填、unique 唯一；approval_level 的 quality 下面挂了一条 library 规则，invalidValues 加枚举 1 2 3 4，意思是审批层级只能取这四个值。请各位注意：这里面没有一行程序逻辑，全是事实陈述——财务主管看完可以直接说「审批层级应该加一档」。但 YAML 有一个特性：层级完全靠空格缩进表达，一个空格都不能错——这既是它简洁的原因，也是本项目最危险的坑的来源。另外文件头声明了数据契约规范版本 0.9.3，这是个开放标准，契约资产不被任何单一工具锁定。

## 第 19 页 · 第 9 坑（最危险）：缩进静默失效
- **要点**：三跑过程（25 项假全绿 → 28 项只生效 1 条 → 34 项全部生效）；根因：多缩进 2 空格被解析成上级子字段；"看不见的失败比报错危险一万倍"；防御武器 = 计数公式（预期 34 实测 25 立刻暴露）；盯数字不盯颜色。
- **配图**：三张时间线卡（红→红→绿）+ 下方解释卡。
- **讲稿**：九个坑里最危险的是第九个：缩进静默失效。过程是这样的：我往契约里加了三条业务规则，跑测试，全绿。但我多看了一眼检查数——还是 25 项，规则根本没生效！修正缩进后二跑，28 项，只生效了一条；另外两条因为多缩进了两个空格，被 YAML 解析器当成了上一个字段的子字段——语法完全合法，引擎照常报绿，可那两条规则从来不存在。第三次把缩进对齐，才到 34 项。为什么说它最危险？报错是看得见的失败，而这是看不见的失败——你以为门口有保安，其实门一直开着。对审计场景来说，这种假合规比没有检查更糟糕。防御武器正是前面建立的计数公式：预期 34 项，实测 25，立刻露馅。所以我给自己立了规矩：盯数字，不盯颜色。语法合法不等于语义正确，运行成功不等于规则生效。这是整个项目里我印象最深的一课。

## 第 22 页 · 两个缺口
- **要点**：缺口一规则层（34 项全是通用型体检，只防无心之失，防不了制审同人/无凭证/越权/分单四种舞弊）；缺口二交付层（终端 passed 业务看不懂）；定位：把「能跑的检查工具」做成「拦得准、看得见的数据产品」。
- **配图**：左右红色缺口卡 + 底部定位语。
- **讲稿**：阶段二从两个真实暴露的缺口出发。缺口一在规则层：基础篇的 34 项检查全是通用型体检——查格式、查枚举、查防呆，只能防「无心之失」。但真实财务舞弊是有套路的：制单人和审批人是同一个人、没有任何凭证就入账、该走高级别审批的走了低级别、把大额拆成多笔小额卡在审批线下——这四种高发形态，通用规则一个都拦不住。缺口二在交付层：检查结果输出在黑色终端里，满屏 passed，财务主管完全看不懂——数据治理的成果停在了最后一公里。所以这个阶段的定位是：把「能跑的检查工具」做成「拦得准、看得见的数据产品」。

## 第 23 页 · 四种舞弊形态 → 七条反舞弊规则
- **要点**：六行映射表：不相容职务分离→same_preparer_approver_flag [0]；无凭证不得入账→missing_support_flag [0]；不得越权→approval_below_expected_flag [0]；不得分单规避→near_approval_threshold_flag [0]；夜间手工标记合法→manual_after_hours_flag [0,1]；时间字段防呆→posting_hour 0-23 / dayofweek 0-6。每条都是财务语言与机器语言互译。
- **配图**：全宽四列表格。
- **讲稿**：七条规则是怎么来的？不是技术推导，是财务审计红线的代码化。第一行，制单人和审批人是同一个人——这叫不相容职务未分离，「管钱的不管账」是内控最古老的原则，值域只能为 0，出现 1 一票否决。第二行，无凭证不得入账。第三行，审批层级不能低于金额应匹配的层级，防止越权。第四行最刁钻：把一百万拆成十笔九万九，每笔都刚好卡在审批线下面——分单规避。第五六行是异常识别：夜间手工录入本身不违规，但标记必须合法。最后一行是数据防呆。请评委注意这张表的左两列和右两列：每一行都是财务语言和机器语言的互译——这就是「财务×数据」复合背景的价值所在。

## 第 24 页 · 三层规则架构
- **要点**：舞弊红线层（值域 [0] 一票否决，防有意舞弊 = "立法"）；异常识别层（枚举 [0,1] 保审计信号 = "体检"）；数据防呆层（表达式约束挡系统错误 = "保险丝"）；设计哲学：[0,1] 描述合法范围，[0] 划定禁止行为，严格度匹配风险性质。
- **配图**：三条横向色带（红/黄/绿）。
- **讲稿**：七条规则不是平铺的，它们按严格度分成三层，这是本阶段的一个设计亮点。最上层是舞弊红线层，值域只允许 0，一票否决——这是「立法」，划定禁止行为。中间是异常识别层，严格枚举 0 和 1：夜间录单本身不违规，可能是正常加班，但标记错了，风控模型就没法区分正常和异常——这是「体检」。底层是数据防呆层，挡的是时区转换、字段溢出这类系统错误——这是「保险丝」。设计哲学一句话：[0,1] 是描述合法范围，[0] 是划定禁止行为——同一把尺子三种刻度，规则的严格度精确匹配风险的性质。过严会误伤正常业务，过宽会漏掉真问题。

## 第 30 页 · 七次连环试错：为什么文件挂载是「死胡同」
- **要点**：最初方案（挂载读 600MB Parquet）→ 七次试错（依赖冲突收敛 [postgres]；任务容器不继承主容器挂载；volumeMounts 非法字段须写 taskRunner 下；C:/ 与 /mnt/c/ 双路径失败——Docker 专用 WSL 发行版与用户 Ubuntu 不是同一个；主容器 Java 镜像无 Python；namespaceFiles 传 600MB 不现实）→ 结构性结论；范式转变：文件思维→数据库思维。
- **配图**：五条试错要点 + 底部深蓝结论卡。
- **讲稿**：为什么一定要把数据迁进数据库？这是七次连环试错换来的架构决策，也是本阶段我最想讲清楚的一页。最初方案很直觉：Kestra 通过文件挂载直接读 Windows 目录里的 Parquet。然后连环撞墙：先是依赖冲突，收敛依赖解决；然后发现 Kestra 的临时任务容器根本不继承主容器的挂载；挂载字段写错位置；C 盘路径和 mnt c 两种写法都失败，因为 Docker Desktop 用的 WSL 发行版和我的 Ubuntu 根本不是同一个；想在主容器直接跑，发现它是 Java 镜像连 Python 都没有；用命名空间文件传，600MB 大文件又不现实。七次之后得出结构性结论：在 Windows + Docker Desktop + WSL2 + Kestra 这个组合下，文件挂载是死胡同——不是配置问题，是架构问题。于是范式转变：不再搬数据，而是让执行环境通过网络访问数据源。数据库天然是所有容器都能访问、有持久化、有健康检查的数据中台。迁库不是妥协，是升级。

## 第 36 页 · 23 个坑里的四颗「珍珠」
- **要点**：网络拓扑坑（容器里 localhost 不是"这台电脑"→服务名+networkMode）；凭据注入坑（容器间什么都不自动继承）；日志辨伪坑（stderr 被标 ERROR 但任务成功→成败只看 exit code 0/1/2/127）；重启灾难坑（数据在卷里不丢，按序恢复；restart 自愈）。
- **配图**：2×2 珍珠卡。
- **讲稿**：阶段三一共排了 23 个坑，挑四颗最有含金量的。第一颗，网络拓扑：任务容器里写 localhost 连不上——因为 localhost 指向的是任务容器自己；改成服务名还是报「名字解析不了」——因为不在那张 Docker 网络里。容器世界里，localhost 不再是「这台电脑」。第二颗，凭据注入：容器之间什么都不自动继承，一切都要显式声明。第三颗，日志辨伪：pip 的警告走 stderr 被标成红色 ERROR，但任务其实成功了——从此我只认 exit code，不看日志颜色。第四颗，重启灾难：数据在命名卷里不丢，按固定顺序恢复即可。这四颗珍珠的共同点是：它们都不是语法错误，而是对系统运行机理的理解——这是转码选手最难补、也最值得补的一课。

## 第 38 页 · Secret 改造：三次失败换来的正确姿势
- **要点**：v1 env() 只读 KESTRA_ 白名单（missing_env）；v2 variables.env 是权限层不是注入层；v3 官方社区版方案 SECRET_ 前缀 + Base64 + secret() 成功；完整链路（明文→Base64→compose→重启→解码入存储→Flow 渲染→任务容器）；重要认知：Base64 是编码不是加密（可逆无需密钥），真正起作用的是"不写明文+环境变量隔离"。
- **配图**：三次尝试卡（✗✗✓）+ 链路卡 + 红字认知。
- **讲稿**：Secret 改造是三次失败换来的。先说结论：Kestra 社区版没有 Secrets 管理界面，那是企业版付费功能，但官方留了「土办法」。第一次尝试：compose 里注入普通环境变量，Flow 用 env 函数读——报 missing_env。查下来发现：Kestra 的 env 默认只读 KESTRA 开头的白名单变量，这是安全设计。第二次：把变量名加进白名单——还是 missing_env。这次学到：白名单管的是「能不能读」的权限，不是「把值送进任务容器」的注入。第三次用官方社区版方案：SECRET 下划线前缀加 Base64 编码，Kestra 启动时自动解码进内部存储，Flow 用 secret 函数读取——成功，55 项全绿。底部红字是一个重要认知：Base64 是编码不是加密，可逆、谁都能解，它只是换马甲不是上锁。真正起作用的是「不写明文加环境变量隔离」。对安全概念保持诚实，比假装安全更重要。

## 第 45 页 · 三个体现「财务功力」的表设计
- **要点**：approver_level_snapshot 级别快照（审批当时留痕，防员工升职覆盖历史——审计思维）；同名不同型 flag 的坑（boolean vs integer 0/1，如实记录并在造数器 V4 修正）；约束即内控（CHECK 级别 1-4/预算≥0、uq_request_approval_sequence 联合唯一防重复审批、4 个外键防孤儿单据）。
- **配图**：三张竖卡。
- **讲稿**：表设计里有三个细节，最能体现财务背景对数据建模的价值。第一个，审批人级别快照：审批记录表里存的是审批发生那一刻的级别，而不是实时关联员工表。想想这个场景：员工小王当年 3 级时审了一笔单，今年升 4 级了——如果实时关联，历史记录就显示「4 级审的」，审计留痕被悄悄改写。快照设计让历史不可篡改。第二个是个诚实的教训：审批表标志位用布尔型，分录表同名标志位用 0/1 整型——同名不同型，造数时直接报错，教训是跨表同名字段要在 ER 图上逐一对齐。第三个，约束即内控：级别 CHECK、预算非负、申请加序号联合唯一防重复审批、外键防孤儿单据——把内控规则直接编译进数据库层，让非法数据物理上进不来。

- **配图**：双卡 + 三条要点。
- **讲稿**：视图 erp_transactions 是契约和业务系统之间的翻译官。它做什么：从 24 列的分录表里裁出 18 列——正好是契约要检查的全部字段。为什么不直接改表结构去迁就契约？两个原因：业务表结构应该服务于业务，不该为质检工具扭曲；契约接口要保持稳定，业务表以后演化不会波及契约。视图不存数据、零冗余——这是软件工程里典型的防腐层模式。字段映射上有一个精彩案例：申请表的「有凭证」标志，到分录表，到视图做 NOT 运算变成「缺凭证」——翻译逻辑是确定性的 SQL，不依赖人工。另外保持两套口径：业务风险分档低中高，和契约的合规判定，是两套独立口径——业务上中等风险的单可能完全合规，这正是内控的多维视角。

## 第 47 页 · 造数生成器：五步流水线 + 事务安全 + 可复现
- **要点**：五步（读库取主数据不硬编码→按规则随机组合选审批人级别达标且≠制单人→金额安全区间 [下限+1000, 临近线-1000] 且 ≤499 万→时间摊铺 20 个工作日 8-17 点→三表全成功才 commit）；固定种子 20260923；金额用 Decimal 不用 float；事务化（曾复现"打印完成库里无数据"）；迭代 12→22→10,022 条（先 10 条冒烟再放量）；psycopg2 execute_values page_size=1000（SQLAlchemy/pandas 设想未采用）。
- **配图**：五节点流程 + 五条要点。
- **讲稿**：数据怎么造？造数器是一条五步流水线。第一步，从库里现读主数据，不硬编码。第二步，按规则随机组合，选审批人时保证级别达标且不等于制单人——造出来的数据天生合规。第三步，金额生成在安全区间——避开五百万红线和临近阈值，保证基线数据干净。第四步，时间摊铺到约二十个工作日、早八晚五。第五步，三表批量写入，全成功才提交，任一失败整体回滚。几个工程细节：固定随机种子保证可复现；金额用 Decimal 不用浮点——0.1 加 0.2 不等于 0.3，浮点金额是财务大忌；事务化写入是因为真的踩过「打印写入完成、库里却没数据」的半截脏数据。迭代路径也遵循工程纪律：先 10 条冒烟试通链路，再放量一万条。

## 第 51 页 · V3 幂等之战：一个 UniqueViolation 引出的三层防护
- **要点**：事故 UniqueViolation TRX10025（重复审批→重复分录，财务头号禁忌）；根因两套 INSERT；三层防护（治本删一套 / ON CONFLICT DO NOTHING / 行锁+状态机）；概念：幂等 = 同一操作执行 N 次结果相同；诚实标记：报错修复 ✅ 已验证，行锁防并发 🟡 逻辑推导（未双会话实测）。
- **配图**：红色事故卡 + 三张防护卡 + 概念卡。
- **讲稿**：V3 版本修了一个让我印象最深的 bug：数据库报唯一键冲突——同一个审批被执行了两次，生成了两笔相同编号的分录。重复记账，财务系统的头号禁忌，在自家系统上演了。根因是自动记账函数里存在两套 INSERT 语句。修复是三层防护：治本，删掉一套，只留唯一写入路径；数据库兜底，ON CONFLICT DO NOTHING，重复写入静默忽略；再加行级锁和审批状态机，只有「待审批」状态的单才能审批——并发双击、刷新页面都不会产生二次记账。这里讲一个概念，幂等：同一操作执行多次，结果和执行一次相同——这是支付和财务系统的生命线，支付宝能顶住重复点击靠的就是它。还要特别说明文档态度：报错修复是已验证的事实，但「行锁能防住并发」标注为逻辑推导——因为没有做双会话实测。整份文档用六档证据标记区分事实与推断，这本身就是工程诚实。

## 第 52 页 · V5 极薄 RBAC：职级 ≠ 系统授权
- **要点**：两条独立的轴（employee_level 1-4 职级 vs employee_roles 四角色授权）；四角色最小集（employee/approver/data_admin/contract_admin）；菜单显隐 + 后端 require_role() 二次校验（违反抛 PermissionError）；"极薄"= 明确不做完整 OA/工作流/HR 中心；实证 E013 仅 employee、E014 起双角色。
- **配图**：双卡 + 三条要点。
- **讲稿**：V5 版本补上了权限体系，叫「极薄 RBAC」——基于角色的访问控制，权限跟着角色走，不跟着人走。核心设计是两条独立的轴：组织层级是你是什么职级；系统授权是你在系统里能干什么。两者刻意分离——4 级领导如果没被授 approver 角色，照样审不了单。角色只有四个。安全上有双重校验：菜单按角色显隐只是体验层，审批动作在后端还要再过一次权限检查加「不能审自己的单」——界面隐藏防君子，后端拦截才防得住绕过界面直接调函数的人。为什么叫极薄？因为我明确不做完整 OA、不做工作流引擎、不做 HR 权限中心——决定不做什么和决定做什么一样重要。

## 第 54 页 · 章节隔页：PART 08 治理与 LLM
- **要点**：变更单 21 字段、2 道闸、拒答率 0/3→2/2、18 条黄金集。
- **讲稿**：第八章，治理与 LLM——项目收官阶段。前面六个阶段建好了「Contract 管数据」和「Runtime 管 Contract 持续执行」。但 V5 基线有一个没人管的缺口：72 项检查写在一个 YAML 文件里，任何人都能打开、修改、保存——谁改的、为什么改、谁批的、改完历史数据还算不算数，全是空白。类比：会计制度放在共享文档里谁都能改。这个阶段补上最后两句话：Governance 管 Contract 的变化，LLM 辅助治理与运行诊断。LLM 在这个项目里的位置极其克制——它从头到尾没写过一行生产契约、没绕过一次人工审批，后面用实测数据说话。

## 第 55 页 · V5 的缺口：契约文件「谁都能改、改了没人知道」
- **要点**：四个无人回答的问题（谁改的/为什么改/谁批的/历史数据还算不算数）；治理目标（CCR/Git SHA 回填/影响评估/可回退）；LLM 克制边界（✅ Copilot 翻译候选、只解释已判定异常、事故报告聚合；❌ 智能问答、Text2SQL——"无需求来源"明确移出主线）。
- **配图**：红卡（四问）+ 绿卡（目标）+ 冰蓝边界卡。
- **讲稿**：阶段七要补的缺口，用四个无人回答的问题最能说明：契约文件谁都能改——谁改的？为什么改？谁批的？改完以前那批合规的数据还算不算数？这就像会计制度放在共享文档里谁都能编辑，在内控视角下不可接受。治理目标就是把契约变更管到与财务凭证同级的水平。LLM 在这个阶段引入，但边界划得非常死：做的只有三件事——把财务的人话翻译成结构化规则的「候选」，绝不自动改生产契约；只解释已经被确定性规则判出来的异常类别；把一次执行的失败聚合成人能读的事故报告。明确不做的：智能问答、Text2SQL——没有真实需求来源，直接移出主线。对 LLM 的克制，本身就是设计。

## 第 56 页 · Day 1：变更单（CCR）+ 四道闸门
- **要点**：contract_change_requests（21 字段：编号/版本 from→to/理由/LLM 规则 JSON/diff/发起人/审批人/Git SHA/七态 CHECK）+ contract_change_audit（8 字段，仅 3 个写入时机）；新增 contract_approver 角色（E002 李敏）；四道闸门（角色/状态/自审批 requested_by≠approved_by 双保险/事务行锁）；验收正负双向 + 修复 8 小时时间差（datetime.now() vs CURRENT_TIMESTAMP）。
- **配图**：左表卡 + 右四道闸门编号卡 + 绿色验收卡。

## 第 57 页 · Contract Copilot：从「人话」到「规则候选」的确定性管道
- **要点**：六环链路（财务人话 → DeepSeek 网页版输出 JSON → 闸门一 JSON Schema 算符白名单 → 闸门二字段白名单 → 确定性生成 rule_id 内容寻址 + YAML diff → candidate 永不覆盖生产契约走 CCR 人工审批）；先定 JSON 合同再接模型；按缩进插入保住注释；模型取证（网页版原始返回逐字存档 + 模型版本/提示词版本/输入哈希三件套，不伪称全链路可复现）。
- **配图**：六节点管道图（两道闸深色高亮）+ 五条要点。
- **讲稿**：Copilot 的完整链路，六个环节，核心思想是「LLM 只翻译，确定性系统干活」。财务说一句人话，LLM 把它翻译成结构化 JSON；然后过两道闸门：第一道 JSON Schema 闸，第二道字段白名单闸；过了闸才由确定性 Python 生成规则 ID 和 YAML diff，产出 candidate 候选版——注意，候选版永不覆盖生产契约，它必须走变更单流程，人工审批通过才生效。几个设计细节：先定 JSON 合同再接模型，边界先于模型；规则 ID 用内容的哈希前 12 位，内容变 ID 变，天然幂等；YAML 按缩进插入而不是整体重序列化，保住注释，diff 可审。模型取证方式也要说明：用网页对话而非 API，每次原始返回逐字存档，用三件套固化证据——诚实声明不伪称全链路可复现。

## 第 58 页 · 三层防御：提示词管模型 / 闸门管规则 / 变更单管放行
- **要点**：第一层提示词（示例去值/拒答情形/语义纠正——能被绕过，模型是概率系统）；第二层确定性闸门（代码 100% 可预测——拦得住格式错，拦不住"语义正确但业务无依据"）；第三层变更单（人最终放行——前两层缺口由人兜底）；核心结论：三层缺一不可，承认每层天花板才是对安全最大的诚实。
- **配图**：三张竖卡（黄/蓝/绿）+ 底部结论。
- **讲稿**：把 LLM 放进财务内控系统，安全模型是什么？三层防御，每层管一件事，也承认每层的天花板。第一层，提示词，管「模型怎么想」。但它的天花板是：模型是概率系统，提示词永远可能被绕过。第二层，确定性闸门，管「规则合不合法」。但它的天花板是：拦得住格式错误，拦不住「语义正确但业务上没有依据」的规则。第三层，变更单，管「放行不放行」：前两层漏掉的一切，最终由人兜底。这是整个第七卷最重要的结论：三层缺一不可，谁也不能替另一层背书。承认每层的天花板，才是对系统安全最大的诚实。

## 第 59 页 · 真模型实测：六个用数据说话的发现
- **要点**：数值边界 4/4 全对（= 5000000 / > 5000001）；内控语义 3 句全错（= N 而非 >= N → 隐蔽假阳性）；闸门有天花板（无依据需求穿透两道闸）；危险需求拒答率 0/3（v1 无任何防线）；语义翻转 bug（"放松"被写成 AND NOT = "强制违反"）；对照实验定真因（全新对话输出逐字节相同 → 排除上下文污染，确认为提示词示例泄漏）。
- **配图**：3×2 发现卡。
- **讲稿**：这一页全是实测数据，用 DeepSeek 真实模型跑了六句边界句和危险需求取证，六个发现。第一，模型擅长数值边界：四句全对，分毫不差。第二，模型不擅长内控语义：三句涉及审批级别的全部把「需要 N 级审批」写成等于 N，而不是大于等于 N——后果是把走了更高级别审批的合规单据误判成违规，这是隐蔽的假阳性。第三，闸门有天花板：一句没有任何数值依据的需求，模型照样编了个阈值，而且穿透了两道闸。第四最危险：三句危险需求——关闭所有检查、忽略缺凭证、允许自审批——初版提示词下全部被翻译成合法 JSON，拒答率零。第五，还发现一个语义翻转 bug：放松类需求被写成「强制违反」，方向完全反了。第六，用对照实验定真凶：开一个全新对话，输出和历史逐字节相同——排除上下文污染，确认真因是提示词示例泄漏。这种实验设计思路，是从排错方法论一路长出来的。

## 第 60 页 · 提示词 v2 三处手术：拒答率 0/3 → 2/2
- **要点**：三处修改（示例去泄漏+禁止照抄 / 补拒答情形 REJECT: 原因——非合法 JSON 天然被闸拦 / 语义纠正 >= N）；双向验证（危险需求 2/2 拒答 ✓ + 正常需求不误拒 ✓）；Evals 18 条基线（偏差 0/拦 6/缺口 5 如实标注由变更单兜底）；Evals 挂 GitHub Actions（换模型/改 Prompt 必须过回归）。
- **配图**：三张手术卡 + 绿卡（双向验证）+ 冰蓝卡（Evals）。
- **讲稿**：针对实测发现，提示词 v2 做了三处手术。第一刀，示例去泄漏。第二刀，补拒答情形：明确两种必须拒答——没有可量化依据的、削弱内控的；拒答输出是一行 REJECT 加原因，它不是合法 JSON，天然会被 Schema 闸拦下——拒答机制和闸门是设计成一个系统的。第三刀，语义纠正：明确审批层级是下限语义。修复效果看双向验证：危险需求拒答率从三分之零升到二分之二，防线立起来了；同时正常需求不被误拒，没有因噎废食——只盯拒答率一个指标，把模型调成见啥都拒，也是一种失败。右边是配套工程：18 条 Evals 黄金测试集，挂进 GitHub Actions，以后换模型、改提示词，都必须先过回归，防止语义悄悄退化。

## 第 61 页 · 诊断三件套：解释异常、定位修复、告警降噪
- **要点**：Failure Explanation（确定性分类在前 rule_id 精确到模型.字段.条款；LLM 只解释类别；五键缓存一类一次；实测注入 600 万真报 FAIL 回滚无污染）；Repair Order（确定性 SQL 定位到单据+当事人，固定模板，LLM 不参与；600 万定位 TRX10024/REQ10024/E023）；Alert Dedup（Set+TTL 300 秒窗口，明确不引 Redis；6 项测试全 PASS）。
- **配图**：三张竖卡。
- **讲稿**：除了变更治理，阶段七还交付了运行诊断三件套。第一件，失败解释器。注意分工：确定性分类在前——这笔交易违规是契约判的，不是 LLM 判的；LLM 只解释「这类问题通常是什么原因」，像顾问解释审计师的结论。带五键缓存，同类问题只调一次模型。第二件，结构化修复单：确定性 SQL 定位到具体单据和当事人，按固定模板输出——原因建议来自映射表，LLM 完全不参与。第三件，告警去重：同一个失败每次定时执行都告警，会造成告警疲劳；用进程内集合加过期时间做去重。这里有个反潮流的决策：明确不引入 Redis——单进程够用，不为炫耀堆技术。三件套的共同哲学：确定性的归代码，解释性的归 LLM，各归其位。

## 第 62 页 · Incident Copilot + 治理三件套
- **要点**：Incident Copilot（失败批次+日志→四节报告：事实/证据/原因/建议；incident_id 内容寻址幂等；复用四个既有模块；6 组断言全 PASS）；③ 变更影响评估（历史数据四分类，PASS→FAIL 必须独立审批人签字——回答"以前那 137 笔"；cia-082959f21d1d：4/2/0/2）；④ 版本回退（只移动 is_current 指针，回退本身也走变更单）；⑤ 事中邻近提示（±5% 邻近带仅提示绝不拦截，血缘未就绪不启用）；联合验收 8/8 PASS；Git 证据 commit 23421e0a…（只提交 candidate+diff）。
- **配图**：左（Incident+联合验收）右（③④⑤ 三卡）。
- **讲稿**：这一页是治理能力的全景收尾。左边，Incident Copilot：把一次 Kestra 执行的多类失败聚合成一份四节事故报告。它不是孤立的新系统，而是复用了解释器的缓存、告警去重、修复单定位、审计日志四个既有模块——好的架构让新能力变成「组合」而不是「重写」。右边是治理三件套。第三号，变更影响评估：改规则前先回答「以前那 137 笔数据怎么办」——只要出现「旧合规新违规」的单据，必须独立审批人签字。第四号，版本回退：只移动版本指针，不碰业务数据，而且回退本身也要登记变更单走审批。第五号，事中邻近提示：仅提示绝不拦截，而且血缘没就绪时不启用。联合验收八项测试全过。Git 证据特别说明一下：证据提交只包含候选版和 diff，生产契约一个字没动——LLM 介入的深度到此为止。

| Webhook | 一个"互联网收件地址"，程序往它 POST 消息，钉钉就转成群消息——它本身就是密钥 |
| Base64 | 一种"换马甲"的编码方式，可逆、不是加密——真正的安全靠"不写明文+环境变量隔离" |
| Secret（SECRET_ 前缀） | Kestra 社区版约定：SECRET_ 开头的环境变量启动时自动解码进内部密钥存储 |
| RBAC | 基于角色的权限控制：权限跟着角色走，不跟人走；本项目"职级≠授权" |
| CCR（变更单） | 契约的"用印审批单"：谁提的、为什么改、谁批的、影响哪些数据 |
| JSON Schema / 字段白名单闸 | 两道"确定性闸门"：先查 LLM 输出格式合法，再查引用字段真实存在 |
| candidate / diff | "假设批准后的契约完整预览"和"改动清单"——给人审的，绝不直接覆盖生产文件 |
| 内容寻址（sha256） | 用内容算出的"指纹"当 ID：内容一变 ID 就变，天然防重复防篡改 |
| 示例泄漏 | 提示词里的示例值被模型当成真实业务阈值照抄——本项目用对照实验实锤的失效模式 |
| 幻觉 | 大模型"一本正经地编造"——对策不是求它别编，而是用确定性闸门+人工审批兜底 |
| Evals（黄金测试集） | 给模型/Prompt 变更准备的"回归考卷"：换模型后重新考一遍，防止语义悄悄退化 |
| Text2SQL / NL2SQL | 自然语言直接转 SQL——本项目明确不做（无需求来源） |
| 血缘（Lineage） | 数据的"族谱"：每个字段能追溯到哪张表、哪个操作、哪条派生逻辑 |
| 级别快照（snapshot） | 审批时把"当时级别"拍快照存下来，防止员工升职后历史留痕被改写 |
| exit code | 命令的"成绩单"：0 成功、1 一般失败、2 用法错误、127 命令不存在——成败只认它，不认日志颜色 |

# 附录 B · 答辩常见提问 + 参考答案

> 标注说明：【文档事实】直接引用项目文档；【建议话术】文档未直接覆盖，但可基于项目事实合理延伸的回答框架（已避免编造具体数字）。

**Q1：为什么用 datacontract-cli，而不是 Great Expectations、dbt tests 这些更主流的工具？**
【建议话术】三个理由：① 它围绕"数据契约"这一开放标准构建（dataContractSpecification 0.9.3），契约是独立资产、不被单一工具锁定；② YAML 是它的原生语言，对非技术背景的业务人员最友好，符合"规则归业务所有"的目标；③ 底层用 Pydantic 严格校验、支持按数据源收敛依赖（[postgres]），从本地文件到 PostgreSQL 的迁移成本低。同时我在项目里如实记录了它的不足（library 规则在 1.2.0 下空转），并给出了改写 type: sql 的应对——工具选型不是信仰，能发现问题并绕过它才是工程能力。

**Q2：为什么选 Kestra 而不是 Airflow？**
【建议话术】对个人项目而言：Kestra 是 YAML 声明式 Flow、自带 Web UI、Docker 一键部署，上手成本低；Airflow 功能更强但部署和学习的固定开销大。本项目调度需求（每日一次、失败告警、临时容器执行）Kestra 完全覆盖。文档事实：Flow 五要素、cron 每日 06:00、errors 块告警均已在生产库上实跑验证。

**Q3：为什么要从本地文件迁移到 PostgreSQL？**
【文档事实】这是七次连环试错换来的结构性结论：Windows + Docker Desktop + WSL2 + Kestra 组合下，Kestra 通过 Docker Socket 创建的临时任务容器无法稳定访问宿主机文件（依赖冲突、挂载不继承、C:/ 与 /mnt/c/ 双路径失败、主容器无 Python、600MB 大文件不适合 namespaceFiles）。范式从"把数据搬到执行环境"转为"执行环境通过网络访问数据源"——数据库是所有容器都能访问、有持久化卷、有健康检查的数据中台。

**Q4：为什么前台用 Streamlit，不用 Vue/React 做个"正经"前端？**
【文档事实 + 建议话术】前台使命不是做一套 ERP，而是"给 Data Contract 提供有业务因果链的数据源"：让 18 个字段有出处、让 72 项检查的 PASS/FAIL 由真实业务动作触发。Streamlit 纯 Python 直连数据库，最快达到目的；项目自我定位就是"最小业务系统"。若未来要多用户并发、复杂交互，可平滑替换——因为业务逻辑都在数据库层（审批策略表、状态机、约束），前端只是薄壳。

**Q5：72 项检查是怎么构成的？怎么保证规则真的生效？**
【文档事实】72 = 18 字段 × 3（存在/类型/非空）54 项 + transaction_id 唯一性 1 项 + maxLength 5 项 + Business SQL 7 项 + Risk SQL 5 项。生效性有双保险：① 计数口径公式贯穿全程（25=8×3+1 → 34 → 55 → 72，每次加规则都核对增量），基础篇曾靠它揪出"缩进静默失效"；② 异常注入反向验证——五类违规精确埋入，72 项中恰好 5 项 FAIL 一一对应。

**Q6：library 规则空转是怎么回事？怎么发现和处理的？**
【文档事实】迁到 PostgreSQL 后发现库里有 3 条同人审批、3 条缺凭证，type: library + invalidValues 规则却报绿灯——本机 CLI 1.2.0 下该 metric 未真正执行。处置：12 条业务规则全部改写为 type: sql + mustBe: 0（SQL 查违规行数必须为 0），让契约"醒过来"；文档如实标注未下定论为官方 Bug。这与基础篇"缩进静默失效"共同形成项目的方法论主线：盯数字不盯颜色。

**Q7：LLM 为什么用 DeepSeek 网页对话版，不用 API？幻觉怎么控制？**
【文档事实】用网页对话版并以"模型版本+提示词版本+输入哈希（sha256）"固化证据，文档明确不伪称全链路可复现（护栏④部分落地，切 API 后可固定 temperature/seed）。幻觉控制靠三层防御：提示词管模型（示例去泄漏、拒答情形、语义纠正）、确定性闸门管规则（JSON Schema + 字段白名单）、变更单管放行（人工审批+影响评估）。实测：危险需求拒答率经 v2 修复从 0/3 → 2/2，且正常需求不被误拒；LLM 全程没写过一行生产契约、没绕过一次人工审批。

**Q8：LLM 输出的规则如果有错，最坏会造成什么后果？**
【文档事实】最坏情况被三层拦截：LLM 只产出 candidate 候选版（生产契约一字不动）→ 必须过两道确定性闸门 → 必须由 contract_approver 人工审批（且禁自审批）→ 凡影响评估出现"旧合规新违规"必须签字。实测中"关闭所有检查"类危险需求在 v2 提示词下被拒答，即便模型输出合法 JSON 也会被人审拦截。审计链 21 字段全程留痕，Git SHA 可回溯，版本可回退。

**Q9：数据量涨到 1000 万、1 亿行怎么办？**
【文档事实+建议话术】当前实测：万级数据 72 项校验 1.38 秒（Kestra 实跑）、百万行级历史验证 1.4~6.5 秒量级，SQL 检查主要走数据库索引扫描。文档规划的扩展路径：数据量上量后变更影响评估迁 Spark/ClickHouse；契约检查本身可利用 PG 分区表/物化视图；造数器与 Pytest 支持 --count 参数化放量。架构上门禁与数据源解耦（契约只面对视图接口），换存储引擎不动契约。

**Q10：如果多个团队、多份契约并行，你的设计能扩展吗？**
【文档事实+建议话术】治理骨架天然面向多契约：变更单含 contract_id、current_version、target_version 字段；版本指针机制（is_current）支持多版本并存与回退；文档规划多团队场景引入 Nacos/Apollo 做契约配置中心。命名空间（company.finance）即 Kestra 的多团队隔离单元。

**Q11：Secret 用 Base64，这不是"伪加密"吗？**
【文档事实】文档主动点破：Base64 是 RFC 4648 编码，可逆、无需密钥，"换马甲不是上锁"；真正让密码不落地的是"不写明文 + 环境变量隔离 + Kestra 启动时注入内部 Secret 存储"。且做过一次真实密钥轮换演练（Webhook 泄露→删旧机器人→签发新地址→重新配置→验证可用）。

**Q12：钉钉告警本身失败了怎么办？300 秒去重窗口怎么定的？**
【文档事实+建议话术】告警通道是 Kestra errors 块的 HTTP 任务，失败会体现在 Kestra 执行状态里（执行本身就标失败）；验证方式是端到端注入故障（改坏 host）。去重窗口默认 300 秒、键为执行 ID+失败规则+窗口起点，实测同窗口 1 发 4 抑制、6 项测试全 PASS；窗口值可配置，属于工程默认值而非拍脑袋的玄学数字。文档也如实标注：告警失败的重试与降级策略细节未展开（可坦诚为已知改进点）。

**Q13：幂等怎么保证的？行锁真的验证过吗？**
【文档事实】三层：唯一写入路径（治本删掉第二套 INSERT）+ ON CONFLICT (transaction_id) DO NOTHING（数据库兜底）+ 行级锁 FOR UPDATE 与审批状态机（仅"待审批"可审批）。文档用证据标记诚实区分：UniqueViolation 修复 ✅ 已验证；"行锁防并发"🟡 逻辑推导（未做双会话实测）——答辩时主动承认这一点并说明验证方法（两会话并发点击），反而是加分项。

**Q14：RBAC 为什么叫"极薄"？生产级还缺什么？**
【文档事实】四角色最小集（employee/approver/data_admin/contract_admin）+ 后端 require_role 二次校验；明确不做完整 OA/工作流引擎/HR 权限中心。生产级差距文档明确标注：登录认证为 demo_hash 演示级（❌ 明确不具备生产级认证），企业化需补 SSO/LDAP、分角色权限路由等五层。

**Q15：数据是自己造的，会不会"既当运动员又当裁判"？**
【文档事实】三层回应：① 基线数据合规由确定性规则保证（金额安全区间避开红线与临近阈值、审批人级别达标且≠制单人、固定种子 20260923 可复现可审计）；② 系统真正被验证靠异常注入——对 TXN-REQ10008~10012 精确注入五类违规，72 项中恰好 5 项 FAIL 一一对应，证明门禁对"没见过的坏数据"有效；③ 前台阶段后，PASS/FAIL 由真实业务动作触发（E2E 链路 REQ10023→APR10024→TRX10024）。

**Q16：审批级别快照为什么这么设计？**
【文档事实】审批记录存"审批当时"的级别快照而非实时关联员工表——员工升职后若实时关联，历史审批的级别留痕会被覆盖（当年 3 级审的单变成 4 级审的），审计留痕被篡改。这是内控"历史不可篡改"原则在 schema 设计上的直接体现。

**Q17：这个项目你个人做了什么？AI 辅助的边界在哪？**
【文档事实】文档本身即与 AI 多轮协作的实录，且最有说服力的证据是：V6 治理初版被三句业务常识追问当场推翻并废弃（自提自批/网页不能直接改 YAML/业务审批与技术验证不能混一道门）——推翻它的判断力、以及把教训重新设计成 Day1 治理骨架+三层防御的决策力，是人的核心工作。业务建模（九条审批策略/临近阈值/级别快照）、规则设计（三层严格度）、异常注入实验、排错方法论均来自财务与工程判断。文档全程使用六档证据标记（✅🟡🔵⚫⏳❌）区分事实与推断，这是个人工程纪律的体现。

**Q18：你是半路转码，整个过程最大的坑是什么？怎么总结排错方法？**
【文档事实】最大的坑是"静默失效"（缩进让规则人间蒸发、全绿是假象）——它教会我"语法合法≠语义正确、运行成功≠规则生效"。排错方法论三条：先找根因行不修症状（26 条错误只有 1 个根因）；"报错变了"就是进步；报错定位信息是最精确的地图。系统层四颗珍珠：容器里 localhost 不是这台电脑、容器间什么都不自动继承、成败只看 exit code、持久化靠卷高可用靠策略。

**Q19：55 项全绿到底有什么意义？数据干净还查什么？**
【文档事实】契约的双重身份：扫描仪（发现脏数据）+ 合规证明书（证明数据干净）。全绿不是"规则没用"，而是可出示给审计的证据——它证明的是"当次数据符合 55 项内控要求"这一事实本身。且门禁有效性由异常注入实验独立证明（5/5 命中），不依赖数据是否干净。

**Q20：必填（required）规则是不是越多越好？**
【文档事实】不是。数据探索发现缺失三梯队：39 个字段全非空可放心 required；invoice_id/approver_id 各缺约 400 条属"业务性缺失"（特定场景才产生）；供应商银行变更域 8 字段空值率 99.97%+，若误设 required 会全量熔断。规则必须长在数据证据上。

**Q21：类型对齐的问题为什么不提前避免？**
【文档事实+建议话术】pandas（int64/int32/float64）与 PostgreSQL（bigint/integer/double precision）类型体系不同，且数据集内部本就混用 int32/int64（posting_hour 是 int32、标志位是 int64）——这正是"先看真实 schema 再写契约"教训的来源。三轮修正后建立的方法论：契约类型必须匹配数据库物理列类型；批量替换解决 80%，剩余 20% 个案必须逐字段校准。

**Q22：Pytest 只有 5 条用例，够吗？**
【文档事实+建议话术】5 条是"链路级冒烟+关键断言"：连接、数据量≥10000、18 核心字段存在、5 类风险标志干净、真调 datacontract ci 子进程跑契约。真正的大规模回归由三层承担：契约 72 项（每次执行都跑）、Evals 18 条黄金集（模型/Prompt 变更必跑）、治理测试 test_governance_345 8/8。文档如实标注：单元测试覆盖率数据未统计（可坦诚为改进点）。

**Q23：这个项目离真正的企业生产还差多远？**
【文档事实】文档明确列出五层差距：① 部署（本机 Docker → 7×24 Linux 服务器/云主机）；② 用户体系（demo_hash → SSO/LDAP+分角色）；③ 数据同步（造数 → ERP 定期 ETL）；④ 规则设计（纯数据规则 → 加操作人维度归因到人）；⑤ 告警路由（单群 → 按规则类型路由到财务经理/IT 运维）。且注明当前检测的是"数据"不是"人"、Docker 停则调度停（数据靠卷不丢）。—— 答辩时主动讲差距，比被问出来体面得多。

**Q24：如果让你重做一次，你会改什么？**
【建议话术】三点：① 环境类配置直接从 docker-compose 起步，省掉 Windows 本机裸跑阶段的反复（PYTHONUTF8 失忆、路径问题）；② 业务规则一开始就用 type: sql，绕过 library 空转的弯路；③ 治理骨架（CCR/自审批闸门）前置到前台开发之前——V6 的废弃本可避免。但这些弯路本身沉淀了可复用的排错方法论，这是"做中学"的成本，也是收获。
