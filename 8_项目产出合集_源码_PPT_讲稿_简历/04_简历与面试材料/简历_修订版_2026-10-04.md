## 一、可以直接粘贴的正文

### 技术栈

Python / PostgreSQL / Streamlit / Data Contract（datacontract-cli）/ Kestra / Docker / GitHub Actions（CI）/ Pytest / LLM（DeepSeek）/ SQL

### 项目简介

面向企业采购、研发、销售等场景，构建从员工业务申请、审批流转、财务交易生成，到数据质量校验、自动化告警及 LLM 辅助契约治理的一体化 ERP 数据契约模拟平台；以"契约管数据、治理管契约变更、LLM 辅助治理与诊断"为主线，所有能力均围绕让 Data Contract 的检查更有意义而构建。

### 核心工作

**1. ERP 业务系统**
基于 PostgreSQL 设计员工、项目、业务申请、审批政策、审批记录、财务分录等核心数据模型；使用 Streamlit 实现员工登录、业务申请、我的申请、审批中心及业务信息可视化，表单中的员工、项目、业务类别及审批规则由数据库动态驱动。

**2. 业务数据自动生成**
根据员工提交的业务申请自动匹配 `approval_policies`，计算所需审批级别并生成审批记录；审批通过后自动形成 `journal_entries`，通过 `erp_transactions` 视图向数据治理层提供标准化财务交易数据。

**3. Data Contract 数据治理**
使用 YAML 定义 ERP 财务核心数据契约，对 18 个核心字段实施字段存在性、类型、非空、唯一性、长度及 SQL 业务规则检查，共执行 72 项检查，覆盖金额上限、审批层级、职责分离、支持性文件、审批阈值等财务内控规则。

**4. 自动化质量门禁**
使用 Kestra + Docker 构建数据质量自动化流程，每日定时执行 Data Contract；在 10,000+ 条 ERP 交易数据上完成 72 项检查并全部通过，并通过异常注入验证金额超限、职责未分离、缺少支持文件、审批层级不足、审批阈值异常等规则的识别能力。

**5. 自动化测试与监控**
使用 Pytest 建立数据库连接、数据规模、Schema 完整性、风险字段及 Data Contract 执行结果的自动化回归测试；使用 Streamlit 构建业务信息可视化与数据质量状态展示，呈现交易规模、金额、风险等级、内控异常及 Contract 检查状态。

**6. LLM Contract Copilot（核心）**
引入 LLM 构建自然语言规则编排能力，将财务人员的自然语言要求解析为结构化规则，经 Schema 校验与字段白名单两道闸门后，由确定性 Python 生成标准 Data Contract YAML 草稿（candidate）；**规则 ID 由规则内容寻址生成（`copilot_{signature}`），与 LLM 输出无关，保证同一规则恒定同一 ID**；落地四条硬护栏（不直接写生产 YAML、不直接执行变更、输出必过 Schema、固定 model/prompt 版本且 temperature=0 以保证语义回归可复现），产出物只有 candidate 与 diff 两个文件，绝不覆盖生产契约、须走变更单审批。**LLM 只负责"理解人话"，分类、编号、生成、比对全部由确定性代码完成。** 通过真模型取证（DeepSeek）发现"模型善数值边界、不善内控语义方向"（如审批级别应 ≥N 却写成 =N）及危险需求拒绝率 0/3 等问题，并以提示词版本化（rule-extract-v2）将拒答率提升至 2/2，沉淀为 Evals 回归集。

**7. Contract 变更治理**
设计 Contract Change Request 与审计链路，对新增或修改的数据契约建立版本指针（from_version / to_version）与审计机制；落地独立审批资格（后端强制 `requested_by ≠ approved_by`，新增 `contract_approver` 角色，资格只看角色不绑定职级），并将 Git 提交作为技术证据回填变更单，配套防重复提交幂等；契约候选版本的发布留作人工待发布决策。

**8. 契约变更的三项治理能力**
围绕"规则改完之后怎么办"补齐三项能力：③ **变更影响评估**——新旧契约各跑一份检查结果，按 `(transaction_id, rule_id)` 对齐做四分类（PASS→PASS / PASS→FAIL / FAIL→PASS / FAIL→FAIL），凡出现 PASS→FAIL 一律要求 `contract_approver` 签字，回答"改完规则以后，以前那些数据怎么办"（示例报告四分类 4 / 2 / 0 / 2，触发签字）；④ **契约版本回退**——只移动契约版本指针，业务账一笔不动，且回退动作本身也生成一条待审批变更单（回退同样要被治理）；⑤ **事中拦截**——提交前对阈值邻近的历史交易给出客观提示，**仅提示、绝不拦截**，且严格排在第一项能力之后落地。三项共 8 条单元测试全部通过。

**9. LLM Failure Explanation 与修复闭环**
对失败做确定性聚类（按命中规则分类），LLM 仅解释已确定的异常类别，并以"契约版本 + 规则 + 错误签名 + 提示词版本 + 模型版本"为键做一类一次缓存；失败时由确定性 SQL 定位源表、责任人与字段，生成结构化修复单（LLM 不参与定位），并用进程内 Set / TTL 对同一执行、同一规则、同一时间窗口的重复告警去重（不引 Redis），输出合并简报。

**10. Incident Copilot（事故聚合诊断）**
在失败解释之上，把一次执行的失败批次与 Kestra 执行日志聚合为四节结构化事故报告（已确认事实 / 异常证据 / 潜在原因 / 修复建议），incident_id 走内容寻址保证同一事故重复生成结果一致；复用既有聚类、去重、修复单、审计四个节点，不重造轮子。与失败解释的分工：失败解释回答"这一类为什么失败"，事故报告回答"这一次执行到底出了什么事、该怎么修"。

**11. Evals 黄金数据集与 CI 门禁**
建立 18 条 Evals 黄金数据集，覆盖阈值边界（500 万以下 / 恰好 / 超过 / 超边界最小单位）、自然语言边界（以上 / 超过 / 不超过 / 至少）与三类危险需求（关掉所有检查 / 忽略 missing_support_flag / 允许申请人审批自己），基线偏差 0、闸门拦下 6、缺口 5（缺口 5 是实测结论，故意不计入失败，由人工审批兜底）；将离线回放写成 GitHub Actions 工作流作为合并前门禁，保证换模型 / 换 Prompt / 换代码后语义不回退。

**12. LLM 交互审计与 PII 脱敏（跨切面护栏）**
每次抽取写审计日志（request_id / model / prompt_version / input_hash / 脱敏摘要 / output / timestamp / operator），可顺变更单追溯；使用外部模型时前置 PII 脱敏（邮箱 / 手机 / 身份证正则掩码），日志仅记录结构化交接点、不留存可还原个人数据。

**13. 架构与边界声明**
绘制数据面、LLM Copilot、跨切面审计、变更治理、Evals 与运行诊断的关系图，并在图上区分**已实证**与**待触发条件**两类：已实证部分给出可打开的代码与产物，待条件部分（如 PostgreSQL 环境实跑、Kestra execution API 真实取数、CI 在远端 runner 上执行）明确标注触发条件，避免把规划讲成已完成。

## 四、三个千万别说错（追问时的生死线）

1. **不要说有多角色审批（法务 / CFO / CEO）**——只落地了**独立审批资格**（`requested_by ≠ approved_by` + `contract_approver` 角色）。说多了会被问穿。
2. **不要把两道闸说成"能拦住一切"**——实测缺口 5 条：字段名对、数值合法，但方向和阈值是编的。这个天花板由变更单的人工审批兜底，不要藏。
3. **NL2SQL / SQL Copilot / 数据分类 Copilot 不属于本项目交付**——它们是明确移出主线的方向，写进简历会被追问"这和契约治理什么关系"。

## 五、一句话主线（开场用）

> Contract 管数据，Runtime 管 Contract 的持续执行，Governance 管 Contract 的变化，LLM 只辅助治理与运行诊断——判断权与定位权始终留在确定性代码手里。判断一个功能该不该做，只看一件事：它能不能让 Contract 的检查变得更有意义。
