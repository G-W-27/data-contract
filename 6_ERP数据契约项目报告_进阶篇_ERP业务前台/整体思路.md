# 一、项目到底解决什么问题

一句话：**给 Data Contract 提供一条具有业务因果链的数据源。**

判断一件事该不该做，本项目只有一条标准：**它能不能让 Contract 的检查变得更有意义。** 凡是不能的，一律不做。这条标准贯穿 V1 到 V6 的全部取舍。

---

# 二、原来为什么不够

上一卷收口时已经有一条跑通的链路：

```text
generate_demo_data.py
        ↓
   PostgreSQL
        ↓
  erp_transactions（视图）
        ↓
   Data Contract（72 checks）
        ↓
Kestra / 钉钉告警 / Pytest / Dashboard
```

它有两点不足。

**第一，源头是脚本，不是业务。** 所有数据由一个 Python 脚本按设想的业务规则写进数据库。它能证明的是"Contract 能检查一份数据"，证明不了"Contract 能检查一套正在运转的业务"。

**第二，因果方向是反的。** 生成器先掷骰子决定 `risk_class` 是 HIGH 还是 LOW，再倒推一笔交易；真实世界的顺序相反——先有一笔具体的业务，再由制度算出它该不该被标红。

用财务的话说：原来那套东西是手工做的模拟账本，记账员和业务经办人是同一个人，账做得再规范也是自说自话。

# 三、为什么必须补 ERP 业务前台

补的是一个真人参与的前台，让数据由业务动作产生。补完之后链路变成：

```text
员工登录 → 提交业务申请 → 匹配审批政策 → 自动路由审批人
   → 审批人审批通过 → 自动生成财务分录 → 进入 erp_transactions
   → Data Contract 检查 → Kestra 调度 → Dashboard 展示
```

四个理由。

**一是字段要有产地。** Contract 检查的 18 个字段，每一个都对应一个真实业务动作：谁提的、属于哪个项目、金额多少、走了几级审批、审批人是不是申请人本人、有没有踩在审批阈值边上。生成器可以按概率把这些字段"抖"出来，但抖出来的没有因果。

**二是字段要由制度算出。** 一笔 18 万的设备采购为什么必须走 3 级审批，只有走完"匹配 POL002 → required_level = 3"这条链路才有答案。

**三是职责分离要真实存在。** 审批人不能是申请人本人，这条内控要求只有存在两个真实登录账号时才可能被违反、也就才可能被检验。

**四是单一事实来源。** 页面上的员工、项目、业务类型一律从数据库读，不另立一套主数据；否则前几卷做的 Data Contract 就失去意义。

它与数据质量看板的分工是清楚的：

| | ERP 业务前台 `erp_app.py` | 数据质量看板 `app.py` |
| --- | --- | --- |
| 使用者 | 业务人员 | 数据治理人员 |
| 动作 | 提交申请、审批 | 查看检查结果 |
| 写入 | 写业务表 | 只读 |
| 回答的问题 | 这笔业务怎么发生的 | 这些数据合不合规 |

两者分开，是为了让"产生数据的人"和"检查数据的人"在系统和职责上都分开。

# 四、最终业务架构

```text
┌─────────── 业务侧（产生数据）───────────┐
│  员工登录 → 业务申请 → 审批 → 自动记账   │
│        Streamlit erp_app.py            │
└──────────────────┬─────────────────────┘
                   ↓
┌─────────── 数据侧（承接数据）───────────┐
│  PostgreSQL → erp_transactions（视图）  │
└──────────────────┬─────────────────────┘
                   ↓
┌─────────── Contract ───────────────────┐
│  18 个字段 / 72 项检查 / YAML 声明式规则 │
└──────────────────┬─────────────────────┘
                   ↓
┌─────────── Runtime ────────────────────┐
│  datacontract ci / Kestra / 钉钉 / 看板 │
└──────────────────┬─────────────────────┘
                   ↓
┌─────────── Governance（🔵 规划）────────┐
│  谁提议改契约 / 谁审批 / 如何验证 / 发布 │
└────────────────────────────────────────┘
```

四层的关系是：**Contract 管数据，Runtime 管 Contract 的持续执行，Governance 管 Contract 的变化，LLM 辅助 Governance 与运行诊断。**

这里最容易混淆的一点是 Governance 与 Contract CI 的分工。Contract CI 是技术验证，回答"改完之后还能不能跑通、数据还合不合规"；Governance 是业务授权，回答"谁批准你把这个阈值从 500 万改成 800 万"。**用技术验证去回答业务授权问题，等于把两个问题混成一个。** 这是 V6 被废弃的根本原因之一。

# 五、数据库关系

## 5.1 关系图

```text
   employees ──┬──> employee_roles          （这个人被授予什么系统能力）
               │
               └──> business_requests <──── projects
                          │                （这笔业务归属哪个项目）
                          │
                          ↓
                    approval_records <───── approval_policies
                 （谁按什么规则审批了什么）        ├──> required_level（要走几级）
                          │                    ├──> gl_account（进哪个科目）
                          ↓                    └──> near_threshold（是否临近阈值）
                    journal_entries
                 （形成了什么财务事实）
                          ↓
                    erp_transactions
                 （给 Data Contract 的稳定接口）
                          ↓
                    Data Contract（72 checks）
```

## 5.2 每张表在说什么

| 表 | 一句话 | 类比 |
| --- | --- | --- |
| `employees` | 人是谁 | 人员档案 |
| `employee_roles` | 人被授予什么系统能力 | 岗位说明书 |
| `projects` | 业务归属到哪个项目 | 项目台账 |
| `approval_policies` | 制度是什么 | 报销制度条文 |
| `business_requests` | 业务提出了什么 | 报销单 |
| `approval_records` | 谁按照什么规则审批了什么 | 报销单上的审批签字 |
| `journal_entries` | 最终形成了什么财务事实 | 装订好的记账凭证 |
| `erp_transactions` | 提供给 Data Contract 的稳定接口 | 交给审计师的凭证册 |

主线只有一条：`employees → business_requests → approval_records → journal_entries → erp_transactions → Data Contract`。左边挂着的 `employee_roles` 与能力有关，右边挂着的 `projects` 和 `approval_policies` 是业务与制度的取数来源。

# 六、V1 → V5 版本总览

| 版本 | 做了什么 | 解决了什么问题 | 留下了什么 |
| --- | --- | --- | --- |
| **V1** | 员工登录 + 提交业务申请 | 第一笔数据由真人动作产生 | 只产生申请，没有审批与记账 |
| **V2** | 我的审批 + 自动记账 | 业务链与治理链第一次接上 | 有并发重复风险；多个风控字段写死 |
| **V3** | `ON CONFLICT` + 行锁 + 状态机 | 幂等与并发保护 | 多个字段"有值但没有真实来源" |
| **V4** | 18 个 Contract 字段来源审计与补全 | 每个字段都有可追溯来源 | 权限只有前端隐藏，没有后端校验 |
| **V5** | 极薄 RBAC | 关键动作有后端授权校验 | 达到稳定基线 |

**V5 是当前稳定基线。** 正式版本链到此为止：V1 → V2 → V3 → V4 → V5。

关于 V3 的两处设计需要说明的是：幂等采用 `ON CONFLICT (transaction_id) DO NOTHING`，它在数据库层阻止重复主键，但无法阻止"审批按钮被重复执行"，因此叠加了行锁 `FOR UPDATE` 与"只有待审批状态可审批"的状态检查。三层各管一段，任一层失效时另外两层仍能兜住。

关于 V3 证据强度的说明见第十二章第 9 条。

# 七、18 个 Contract 字段来源总览

## 7.1 统一口径

V4 完成后，结论统一表述为：

> **18 个 Contract 字段全部具有明确、可解释、可追溯的来源或确定性派生逻辑。**

这个说法不能简写成"18 个字段全部来自业务输入"。实际来源分为七类：业务输入、主数据 / 政策、系统生成、系统标识、派生计算、风险计算、系统规则。

## 7.2 完整审计表

| Contract 字段 | V3 来源 | V4 来源 | 来源类型 |
|---|---|---|---|
| transaction_id | approval_id 派生 | approval_id 派生 | 系统生成 |
| erp_system | 数据库默认值 | 显式写入 ERP_DEMO | 系统标识 |
| posting_datetime | CURRENT_TIMESTAMP | CURRENT_TIMESTAMP | 系统生成 |
| amount | business_requests.amount | business_requests.amount | 业务输入 |
| currency | business_requests.currency | business_requests.currency | 业务输入 |
| gl_account | approval_policies.gl_account | approval_policies.gl_account | 主数据 / 政策 |
| manual_entry_flag | 写死 0 | 业务事实为 0 | 系统规则 |
| risk_class | 写死"普通" | 多风险字段综合计算 | 风险计算 |
| approval_level | required_level | approver_level_snapshot | 业务规则 |
| is_round_amount | amount 计算 | amount 计算 | 派生字段 |
| high_value_flag | amount 计算 | amount 计算 | 派生字段 |
| posting_hour | CURRENT_TIMESTAMP 提取 | CURRENT_TIMESTAMP 提取 | 派生字段 |
| posting_dayofweek | CURRENT_TIMESTAMP 提取 | CURRENT_TIMESTAMP 提取 | 派生字段 |
| same_preparer_approver_flag | 写死 0 | requester_id == approver_id | 风险计算 |
| missing_support_flag | 写死 0 | support_document_flag 反向映射 | 风险计算 |
| approval_below_expected_flag | 写死 0 | approver_level_snapshot < required_level | 风险计算 |
| near_approval_threshold_flag | approval_records 同字段 | approval_records 同字段 | 业务规则 |
| manual_after_hours_flag | 写死 0 | manual_entry_flag + posting_hour 派生 | 风险计算 |

V3 里有 5 个字段是 SQL 中写死的常量，V4 把它们逐一接到真实业务关系上。

## 7.3 三层血缘

`missing_support_flag` 是最典型的一条，它穿过三张表：

```text
申请页"有没有支持性文件"复选框
        ↓  business_requests.support_document_flag
        ↓  journal_entries.supporting_document_flag
        ↓  erp_transactions.missing_support_flag（反向映射）
```

这条链在 V3 阶段是靠"页面造一张没贴发票的报销单"主动触发 FAIL 才被验证的（✅ 已验证）。

## 7.4 关于 `manual_entry_flag = 0`

这个字段不应当理解为"代码写了 0"。准确口径是：**当前唯一的财务分录生成路径是审批通过后的系统自动记账，因此该业务事实为非人工录入。** 它是一个业务事实的反映，不是硬编码默认值。

由此产生一个连带结论：因为当前不存在人工录入通道，`manual_after_hours_flag` 的真实取 1 场景尚未出现（⏳ 未完成）。

## 7.5 `risk_class` 与快照

`risk_class` 采用一票否决制，不加权：`HIGH` = 同人审批 / 缺支持文件 / 审批层级不足；`MEDIUM` = 接近审批阈值 / 金额 ≥ 500000；`LOW` = 其他。硬伤与软信号不该按权重混合，否则权重会掩盖硬伤。

`approval_level` 使用 `approver_level_snapshot`（审批发生那一刻的审批人级别），而不是 `employees.employee_level`（当前级别）。原因是员工级别会随时间变化，用当前值会让历史交易的审批层级被追溯性地改写。

# 八、V5 极薄 RBAC

## 8.1 两个概念必须分开

```text
employees.employee_level  =  组织 / 业务层级（这个人是什么级别）
employee_roles.role       =  系统授权能力（这个人被允许做什么）
```

**职级够，不等于系统授权。** 一个 4 级员工如果没被授予 `approver` 角色，就不能审批。

角色从员工表里分出来的原因是：新增、撤销、叠加角色都不需要改 `employees` 表结构，而且天然支持一个人有多个身份——一个财务总监可以同时是普通员工、审批人和数据管理员。

## 8.2 四个角色

| 角色 | 能做什么 |
| --- | --- |
| `employee` | 提交业务申请、查看自己的申请 |
| `approver` | 查看并审批分配给自己的单据 |
| `data_admin` | 维护主数据 |
| `contract_admin` | 管理契约相关配置 |

## 8.3 审批人必须同时满足四个条件

```text
员工在职
AND employee_level >= required_level
AND 拥有 approver role
AND approver_id != requester_id
```

四个条件缺一不可：前两个是组织资格，第三个是系统授权，第四个是职责分离。

## 8.4 前端隐藏不是权限控制

页面上看不到某个按钮只算提示，不构成安全边界。所有关键动作在后端用 `require_role()` 重新校验一遍。**真正拦住越权的那一层在服务端。**

# 九、V6 为什么废弃

> ⚫ **V6：Contract Change Governance 初始设计——已废弃。** V6 不属于正式版本链。

## 9.1 V6 最初想做什么

设计一套契约规则的变更治理：管理员在网页上改审批规则，发起变更，走审批流，通过后写入 `financial_data_contract.yaml`。

## 9.2 三个设计问题

**问题一：自己提出、自己审批。** 变更的发起人和审批人是同一个管理员账号，违背职责分离。原始质疑是：

> "他怎么自己提出，自己审批啊"

**问题二：网页直接编辑 YAML，LLM 就没有位置了。** 如果管理员能在网页上直接改 YAML，那么"用自然语言描述变更需求、由 LLM 转成结构化变更"这条路就彻底没有存在必要。原始质疑是：

> "如果我在网页上做更改的话，就没必要接入 LLM 了吧"

**问题三：Governance ≠ Contract CI。** V6 把"治理审批"和"Data Contract CI"混成了同一个"批准"动作。前者是业务授权，后者是技术验证，混在一起等于用技术验证去回答业务授权问题。相关的原始质疑是：

> "Contract Change Governance 这个和契约本身有关系吗"

## 9.3 结论

V6 废弃，V5 保持为稳定基线。V6 之后的方案统一称为**"V6 废弃后的 Contract Change Governance 重构方案"**，不重新编号（🔵 规划，当前未实现）。

重构方案的方向是：只做治理骨架，不做网页 YAML 编辑器。变更路径改为"业务人员提出变更需求 → 说明业务原因 → 获得业务审批 → 技术人员修改 YAML → Pytest → Data Contract CI → 通过后发布新 Contract"，LLM 的角色是辅助自然语言变更与运行诊断。

# 十、最终 E2E 链路

| 环节 | 证据 | 状态 |
| --- | --- | --- |
| 员工登录 | E001 张伟从 `employees` 表被读出并登录 | ✅ 已验证 |
| 提交业务申请 | `REQ10023`（采购 / 设备采购 / 180000 / CNY）落库 | ✅ 已验证 |
| 匹配审批政策 | 命中 `POL002`，`required_level = 3` | ✅ 已验证 |
| 自动路由审批人 | `APR10023` 的 `approver_id = E003`（非申请人本人） | ✅ 已验证 |
| 审批人审批通过 | `APR10024` 状态由"待审批"变为"已通过" | ✅ 已验证 |
| 自动生成 journal_entries | `TRX10024` 由审批通过动作自动生成 | ✅ 已验证 |
| 幂等与并发保护生效 | `TRX10025` 修复后落库，不再报 `UniqueViolation` | ✅ 已验证 |
| 进入 `erp_transactions` 视图 | 视图查询结果可见对应行 | ✅ 已验证 |
| Data Contract 执行 | `🟢 data contract is valid. Run 72 checks.` | ✅ 已验证 |
| 72 checks 双向验证 | `missing_support_flag` 规则 PASS 与 FAIL 均被真实触发 | ✅ 已验证 |
| Kestra / Dashboard / 钉钉 | 前几卷已验证；本卷范围内未重新触发 | 🟡 前卷证据 |

两点必须如实说明。

**第一，不存在单笔业务的全链路追踪记录。** 上表中 `REQ10023` 走到"待审批"就停了，`TRX10024` 有完整记账但没有对应的单笔 Contract 输出。各段都有真实输出，但段与段之间不是同一笔业务。原始实录未保留该输出，此处不补全、不推演。

**第二，72 项检查的准确表述是：** 在当前干净基线下 72 项全部通过；同时通过代表性异常注入验证了关键规则能够产生 FAIL。这不是"72 条规则每一条都获得了充分的异常覆盖"。

# 十三、下一步计划：先有需求，后有功能

> 🔵 以下为规划，尚未实现。不得以任何方式写成已完成。完整版见《ERP业务前台卷》第五章。

判据只有一条：**看这个功能做完之后的产出物是什么。** 产出物是"契约的一次可追溯变更"或"契约规则在业务发生那一刻生效"，它还在主线上；产出物是"一个页面""一套审批流"，它已经偏了。V6 被否掉就是因为它的产出物最终变成了一个网页上的 YAML 配置页面。

第二条规矩同样重要：**功能不能凭空产生。** 每一项改进都必须能指向一个具体问题——要么现在已经存在，要么是上一步做完必然撞上的。写不出问题来源的，不做。

**现在就做（五项）。** ① 契约变更可追溯：`contract_change_requests` / `contract_change_audit` 两张表已建但**没有任何链路往里写**。② 契约变更审批资格：做 ① 必然撞上，`contract_admin` 既是发起人又是执行人，V5 的四个角色里没有契约变更审批人。③ 变更影响评估：改完必须回答"以前那 137 笔呢"，CI 答不了。④ 契约版本回退：Git tag + 版本指针即可，不引配置中心。⑤ 事中拦截：用现有 `near_threshold_amount` 在提交前提示，零新增依赖，是契约规则第一次在业务发生那一刻生效。

**接了 LLM 才做（四项）。** ⑥ Contract Copilot，只做"人话 → 结构化 JSON"，落 YAML 交给确定性 Python；⑦⑧⑨ 成本（异常聚类与缓存）、安全（防注入 + PII 脱敏 + 审计）、Evals（黄金数据集）——**这三件的需求全部由 ⑥ 带来，没有 LLM 时它们都不存在。**

**更远节点，有触发条件，当前不做。** 增量检查与分区、列式/分布式执行、流式检查、数据血缘、契约版本配置中心、异步解耦、监控体系——它们都是上述节点的规模化形态，是同一条路上更远的格子，不是岔路。换引擎的分水岭**不是"数据总量"，而是"单次检查窗口 + 实时性要求"**：Contract 检查的是"本次要放行的数据"，不是全量历史。

**已移出计划。** Incident Copilot、SQL Copilot——没有任何需求来源。

顺序不可并行：① → ② → ③ → ④ → ⑥ → ⑦⑧⑨。依据是 V6 的教训——先做网页改 YAML，LLM 就彻底没有位置了。

# 十四、三分钟项目讲述版

**起点。** 原来有一条 `generate_demo_data.py → PostgreSQL → Data Contract` 的链路，72 项检查全绿，Kestra 定时跑，失败钉钉告警。但它只能证明"Contract 能检查一份数据"，因为数据是我自己造的，而且因果是反的——先掷骰子定风险等级，再倒推交易。

**做了什么。** 补一个 ERP 业务前台，让数据由真人操作产生：员工登录、提交申请、系统按金额匹配审批政策、自动路由出一个不是申请人本人的审批人、审批通过、自动生成财务分录、进入视图、被 Contract 检查。V1 打通申请，V2 补审批与记账，V3 用 `ON CONFLICT` + 行锁 + 状态机解决幂等与并发，V4 把 18 个字段从"有值"改成"有来源"，V5 加一层极薄 RBAC。

**关键难点。** 一是 18 个字段里有 5 个是 SQL 写死的常量，需要逐一接到真实业务关系上；二是字段要用快照而不是当前值，否则历史交易会被追溯性改写；三是风险分级要用一票否决而不是加权，否则权重会掩盖硬伤。

**为什么没做下去。** V6 想做契约变更治理，但设计阶段暴露三个问题：自己提自己批、网页直接改 YAML 让 LLM 无处安放、把治理审批和 Contract CI 混成一个"批准"。所以 V6 废弃，V5 定为稳定基线。

**最终认知。** Contract 管数据，Runtime 管 Contract 的持续执行，Governance 管 Contract 的变化，LLM 辅助 Governance 与运行诊断。

**必须说清的边界。** 这是仿真 ERP 环境中由业务操作产生的演示数据；登录是演示级认证；并发保护没有双会话实测；端到端验收是按环节分别取证的，没有单笔业务的全链路追踪。
