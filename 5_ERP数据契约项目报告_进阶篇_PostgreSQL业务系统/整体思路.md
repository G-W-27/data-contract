## 一、这一卷在回答一个什么问题

前四卷收口时，手里已经有一条跑得很顺的链路：`generate_demo_data.py` 一次性往 PostgreSQL 灌进一万多条 ERP 交易，`erp_transactions` 视图把员工、项目、审批、财务分录拼在一起，后面接 Data Contract（72 项检查）、Kestra 定时调度与钉钉告警、Pytest 兜底、Streamlit Dashboard 展示。工程上看它是完整的，但有一个致命前提：**里面所有的数据都是我自己造出来的**——一个 Python 脚本按我设想的业务规则，把申请、审批、分录一行行「编」进数据库，源头是脚本不是活人。

所以当时做的其实是「数据治理」而不是「业务系统」，治理的是我自己编出来的账。卷四设计稿里那条业务链——员工登录、提交业务申请、审批、形成财务分录——到那时只存在于设计稿里，跑通的只有右侧那个数据治理的世界。卷五要补的，正是这条缺失的「上游」：让数据有一个真实的业务产生源头，而不是一行 `df.to_sql` 直接写进库。

**闭环小结**：因为前序已经能让 Contract 在本地数据上跑通，但数据是自己编的、源头不存在 → 所以卷五把上游业务数据库和数据生产链补起来，再把已有 Contract、Kestra、Pytest、Dashboard 接回去 → 结果：项目从「对现成数据做质量检查」进一步变成「业务系统产生数据、数据治理系统持续检查」的完整链路。

## 二、本卷的两条主线（全文最重要的一个视角）

读这一卷最容易犯的错，是把 PostgreSQL、Python、Data Contract、Kestra、Pytest、Streamlit 看成六个互不相关的工具。必须先建立全局视角：它们其实分属两条并行存在、最终汇合的主线。

**业务数据生产线（数据从哪来）**：员工、项目、审批规则是基础主数据 → 业务申请是员工提交的 → 审批记录是谁批的、合不合规 → 财务事实是审批通过后的交易 → 这些最终汇总进 `erp_transactions` 视图，成为 Data Contract 的统一接口。

**数据治理线（数据对不对）**：Data Contract 定义检查什么 → Kestra 定时执行 → Pytest 做代码/链路回归 → Streamlit 把结果展示给业务人员。

两条线在 `journal_entries → erp_transactions → Data Contract` 这里汇合。必须强调：这不是「单纯把数据库换成 PostgreSQL」，也不是「单纯把数据量从 12 条扩大到 10,000 条」，而是把原型逐步变成有源头、可规模化、可自动校验、可监控的完整数据质量工程链路。

## 三、为什么要从 Parquet 迁移到 PostgreSQL

这一步是整卷的起点，也是最容易被低估的一步。原项目在本地已经用 Parquet 文件跑通了 55 项检查，为什么还要折腾 PostgreSQL？当时考虑了三种方案。

方案 A 是继续用 Parquet 文件，好处是不用改任何东西，坏处是这个文件只在我自己电脑上能读，换一台机器、换一个环境就打不开，而且它本质上是「死文件」，不是「活数据」——谁想查都得先把文件读进某个程序。方案 B 是用 SQLite，好处是轻量、单文件，坏处是不支持并发、不支持 View、不适合生产环境。方案 C 是用 PostgreSQL，好处是它是生产级数据库，支持并发、支持事务、支持 View，任何 BI 工具、任何有权限的应用，只要拿着连接凭据通过网络就能连上去查，坏处是配置比前两个方案复杂。

我最终选 PostgreSQL，因为这个项目的目标本来就不是「本地能跑就行」，而是「生产级数据管道」。真实企业的数据从来不会以 Parquet 文件的形式送给数据团队，它一定在数据库里。用财务的话说，这就像把账从「个人 Excel 表格」升级成「公司财务系统」——Excel 只能自己看，财务系统谁都能连。

而且这个决定不是凭空加技术栈。前序想把 Kestra 任务直接访问本地 Parquet，结果在 Windows / Docker / taskRunner / volume mount 之间反复踩坑，最后放弃文件挂载思路，把数据迁移到 PostgreSQL。所以 PostgreSQL 是为了解决「容器化自动运行场景下的现实约束」才进来的，不是为显得高级硬塞的。

**闭环小结**：因为本地 Parquet 文件是「死文件」、只在我自己电脑上能读 → 所以把数据迁移到 PostgreSQL，让数据变成「活数据」、任何有权限的应用都能连 → 结果：数据管道从「本地脚本」升级为「生产级数据库」。

## 四、6 张表 + 1 个 View：业务被拆成了什么

建库时为什么是这 6 张表，而不是 3 张或 10 张？因为真实企业的数据不是一张大表，而是一条链：员工 → 项目 → 业务申请 → 审批规则 → 审批记录 → 财务事实 → 契约接口。

| 对象 | 类型 | 角色 | 负责回答的问题 |
|---|---|---|---|
| `employees` | Table | 员工主数据 | 谁在做事 |
| `projects` | Table | 项目主数据 | 事情属于哪个项目 |
| `approval_policies` | Table | 审批规则 | 多少钱需要几级审批 |
| `business_requests` | Table | 业务申请 | 员工申请了什么 |
| `approval_records` | Table | 审批记录 | 谁批的、合不合规 |
| `journal_entries` | Table | 财务事实 | 最终形成什么财务交易 |
| `erp_transactions` | View | 契约接口 | Data Contract 实际检查什么 |

关键的认知点有两个。第一，`erp_transactions` 是 **View 不是表**：它不保存数据，只保存查询定义，从底层五张表拼出 Data Contract 要检查的标准化交易。第二，`journal_entries` 才是底层事实表，异常注入要改的是它，而不是这个只读的 View——这正是「为什么异常直接改 `journal_entries` 而不是改 `erp_transactions`」的答案。

每张表都有主键、外键（`fk_project_manager` 等）、CHECK 约束（`chk_employee_level` 等）和中文 `COMMENT ON COLUMN`，因为这些约束本身就是在数据库里落地的财务内控（比如 `approval_level` 取值范围、金额非负）。与财务类比：`employees` 是工号本、`approval_policies` 是审批制度、`business_requests` 是报销单、`journal_entries` 是总账凭证、`erp_transactions` 是给审计看的报表。

**闭环小结**：因为一个真实企业的数据不是一张大表，而是「员工 → 项目 → 业务 → 审批 → 财务」这条链 → 所以把它拆成 6 张表 + 1 个 View，每张表负责一段 → 结果：数据模型既有业务语义，又支持数据血缘追溯。

## 五、数据怎么来：12 条手工 → 生成器 → 10,022 条

我要大量数据来验证 Contract，有几种方案？手工造太慢，从真实数据复制不现实，所以选了「从数据库读基础数据 + 按业务规则随机组合」的方案。但这一步不是一上来就写生成器，而是分了清晰的版本演进：

- **V1 手工 12 条**：先建立最小可运行闭环样本，确认表结构和业务关系成立。
- **V2 初版生成器 + `--count 10`**：冒烟测试，先验证连接、表结构、字段类型、事务逻辑。
- **V3 修 `status` → `project_status`**：报错 `column "status" does not exist`，回查 `\d projects` 确认真实 Schema 是 `project_status`。
- **V4 修 `approval_records` 布尔字段类型**：报错 `is of type boolean but expression is of type integer`，把 `0/1` 改成 `False/True`（注意 `journal_entries` 同名标志是 `integer` 用 `0/1`，两张表类型不能混）。
- **V5 `--count 10000`**：最终实测 **10,022 笔**模拟交易。
- **V6 注入 5 类异常**：Contract FAIL（见第六节）。
- **V7 恢复基线**：五项异常计数归零，回到干净基线。

这里有几个必须钉死的事实边界（卷五校对时重点修正过）：最终真实落地的是 **`generate_demo_data.py` + psycopg2 + `execute_values(page_size=1000)` + 事务 `commit`/`rollback`**，不是把 pandas + `df.to_sql` 当最终实现；`page_size=1000` 控制每次多值 INSERT 拼多少行，不是事务提交次数，事务边界是三张表全部写成功才统一 `commit()`、任一步失败则 `rollback()`；固定随机种子 `RANDOM_SEED = 20260923` 只是让随机选择可重复，不保证「重复执行得到完全相同的库」——生成器是基于当前库里最大 Request 编号追加的；「100 万行」只出现在前期规模讨论里，不是已实现结果。

生成器的逻辑：从 `employees` / `projects` / `approval_policies` 读基础数据 → 按业务类型 + 金额匹配 `approval_policies` 得到 `required_level` → 找满足级别且不是申请人的审批人 → 批量生成三张业务表。金额从安全区间生成、正常数据风险标志全部为 0、固定种子，都是为了让正常基线稳定 PASS、又让后续异常注入可控。

**闭环小结**：因为手工造数据太慢、纯随机又不符合业务逻辑 → 所以写了生成器，从库读基础数据、按规则随机组合、分块写入、事务保护 → 结果：10,022 条符合业务逻辑的模拟数据几分钟内生成，且可复现、可规模化。

## 六、Data Contract 从 55 项到 72 项

这一步要回答「原来 55 项够不够」。55 项更多是通用数据质量（字段存在、类型、非空、唯一性），覆盖不到真实财务风险。卷五把 Contract 升级成覆盖金额防呆、审批越权、职责分离、凭证缺失等内控规则的专项防线。

正确的时间线是：Parquet 阶段 **25 → 28 → 34**，PostgreSQL 对齐后 **55 → 63 → 72**。72 是 Contract 实际执行生成的 checks 数，不是数据库里有 72 条规则——规则本体在 `financial_data_contract.yaml`，数据库只提供 `erp_transactions` 这个被检查的数据接口。

72 项的构成：18 字段基础检查（存在/类型/非空/唯一性 + transaction_id 唯一）→ 加 5 个 maxLength（transaction_id、erp_system、currency、gl_account、risk_class）→ 加 12 个 SQL 业务规则（amount、manual_entry_flag、approval_level、is_round_amount、high_value_flag、posting_hour、posting_dayofweek、same_preparer_approver_flag、missing_support_flag、approval_below_expected_flag、near_approval_threshold_flag、manual_after_hours_flag）。其中 `approval_level` 是 1～4 的审批层级字段，单独算，**8 个 0/1 标志位**不能和它混为一谈。

一个关键修正：旧版 `type: library + invalidValues` 在当前 CLI 版本下没有产生预期的有效检查，所以改成 `type: sql`，由 SQL 直接查询违规数量、`mustBe: 0` 表示「不合格品必须为 0」。这好比审计规则从「通用体检」升级为「专项反舞弊防线」。对「是不是 CLI Bug」保持谨慎：只记录运行现象和本机 1.2.0 / Kestra Task 1.2.1 的版本差异，不擅自下「官方已确认是 Bug」的结论。

**闭环小结**：因为 55 项只是通用体检，覆盖不到具体业务风险 → 所以加了 5 个长度约束 + 12 个 SQL 业务规则 → 结果：Contract 从 55 项升级到 72 项，覆盖金额上限、审批层级、职责分离、支持性文件、审批阈值等财务内控规则。

## 七、异常注入：能执行 ≠ 能发现

正常数据已经 PASS，为什么还要故意改成 FAIL？这是整卷最容易被误解的一步。「Contract 能跑」和「Contract 能抓异常」是两种验证目标。我要验证 Contract 真的能抓住异常，方案是直接在 5 条正常交易上注入异常，而不是改 Contract 本身或造一批脏数据。

5 条异常逐一对应 5 条规则：

| 交易 | 修改字段 | 改值 | 触发规则 |
|---|---|---|---|
| TXN-REQ10008 | `same_preparer_approver_flag` | 1 | 同人审批 |
| TXN-REQ10009 | `missing_support_flag` | 1 | 缺支持文件 |
| TXN-REQ10010 | `approval_below_expected_flag` | 1 | 审批级别不足 |
| TXN-REQ10011 | `near_approval_threshold_flag` | 1 | 接近阈值 |
| TXN-REQ10012 | `amount` | 6000000 | 金额超 500 万 |

选这 5 条，是因为它们都是正常数据，改一条就能干净地验证一条规则；改在 `journal_entries` 而不是 View，因为 View 只读、底层事实在 `journal_entries`。注入后 `datacontract ci` 输出 `was 1, expected = 0`，5 项规则各自被抓出。验证完把 5 条改回正常、异常计数归零，回到干净基线，**不虚构第二次「FAIL → 修复 → PASS」演示**——这是用户明确要求的事实边界。

**闭环小结**：因为「Contract 能跑」不等于「Contract 能抓」 → 所以故意在 5 条正常交易上注入 5 类异常 → 结果：Contract 准确抓出 5 条异常，证明规则对真实业务违规有效。

## 八、Pytest：再铺一层自动回归

Data Contract 已经会检查了，为什么还要写 Pytest？因为两者职责不同：Data Contract 偏向「数据本身合不合格」，Pytest 这一层负责「这个项目整体有没有被改坏」——数据库连接、数据规模、核心字段、风险基线、以及真实 Contract 执行链。

5 项测试：
- `test_database_connection`：确认能连上库（项目基础设施）。
- `test_transaction_volume`：确认数据规模 ≥ 10,000（防规模异常）。
- `test_core_columns_exist`：确认 18 个核心字段全部存在（字段回归）。
- `test_risk_flags_clean`：确认基线数据中 5 类关键风险条件（同人审批/缺支持/层级不足/接近阈值/超限额）全部为 0。
- `test_data_contract`：直接调用真实 `datacontract ci`，验证 Contract 执行链。

实测 **`5 passed in 2.84s`**——2.84 秒是本次运行的耗时，不包装成「永久性能保证」。它的意义是「测试体系可重复执行」，不是「代码没语法错误」。

**闭环小结**：因为手工跑 Contract 不能自动回归 → 所以写了 5 项 Pytest，覆盖连接、规模、字段、风险基线、真实 Contract 执行 → 结果：以后每次改完代码都能一键回归，避免「改坏了自己不知道」。

## 九、中文 Streamlit Dashboard：给业务人员看的大屏

旧版 Dashboard 有两个问题：只读本地旧 JSON 报告（所以一度显示 55/55，而 Kestra 已经实际跑 72 checks），表格列名是英文，财务主管看不懂。新版分三版演进：V1 只读 JSON 统计通过/失败 → V2 直接连 PostgreSQL 展示交易总数、金额、风险分布 → V3 彻底中文化，加入 Data Contract 健康状态、检查明细、最近交易。

必须钉死的边界：Streamlit 是**展示层不是数据源**，它 `SELECT` 当前交易数据再画 KPI/风险分布/Contract 状态；Dashboard 首次加载时独立执行一次 `datacontract ci`（用 `st.session_state` 避免普通 rerun 无限重跑），和 Kestra 每日 06:00 的定时执行是**两个独立的执行过程**，共享同一套规则主体但不是同一次运行；当前是「页面加载或主动刷新时按需查询最新库状态」，没有 WebSocket、没有后台实时推送，不能说「实时同步」。用财务类比：这就像财务系统从「给 IT 看的后台」升级成「给 CFO 看的大屏」。

**闭环小结**：因为旧版只读 JSON、列名英文 → 所以新版连 PostgreSQL、所有列名中文化 → 结果：财务主管不需要懂技术，一眼看到交易规模、金额、风险分布、Contract 检查状态。

## 十、Kestra 里的 Contract：本地与定时两份必须同步

Contract 改了，Kestra 里那份怎么更新？本地那份要不要改？关键事实：Kestra 的 `company.finance` Namespace Files 里有一份 `financial_data_contract.yaml`，本地也有一份，是两份独立文件。Kestra 用命名空间里的那份跑定时任务，本地那份是手动测试用的。两份不一致的后果是：本地通过、Kestra 失败，或者反过来。

所以每次改契约都「两边都改」，除了 `host` 必须不同（本地 `localhost`、Kestra Task 容器用 Compose 服务名 `postgres`），其他规则主体必须一字不差。用财务类比：这就像公司的「报销制度」和「分公司报销制度」——除了地址不同，其他条款必须完全一致。本机 CLI 1.2.0、Kestra Task 实际运行 1.2.1 的版本差异也要如实记录，不虚构「已统一」。

**闭环小结**：因为 Kestra 里的 Contract 和本地那份是两份独立文件 → 所以每次改契约都「两边都改」 → 结果：除 host 因运行位置不同而不同，规则主体一字不差，「双份同步」成为日常纪律。

## 十一、用户追问里最关键的几个认知障碍

卷五校对时把用户反复追问、而旧报告没覆盖透的问题全部单列。这里挑几个最影响「能不能看懂系统」的：

- **「我写的 SQL 在 VSCode 里，为什么半天没看见自己的表？」** 因为 `.sql` 文件只是文本，真正的表在 PostgreSQL 里，SQL 必须被执行才会变成数据库对象；本地文件不会自动进库。
- **「Docker 里为什么找不到表？」** Docker 是运行 PostgreSQL 的容器环境，而 `employees` 等是 PostgreSQL 内部的对象；Docker Desktop 的 Containers/Volumes 视图 ≠ PostgreSQL 的 Table 浏览器。
- **「`\d` 在 PowerShell 里为什么报错？」** `\d` 是 `psql` 元命令，不是 PowerShell 命令，要先进入 `erp_demo=#` 环境才能用。
- **「YAML 契约到底怎么连上数据、谁执行它？」** YAML 只是规则声明 → `datacontract ci` 读取它 → 连接 PostgreSQL → 检查 `erp_transactions`。Flow 负责「什么时候跑、在什么环境跑、失败做什么」，Contract 负责「检查什么、规则是什么」，两者不是一回事。
- **「生成器是不是在模拟真正 ERP？」** 生成器读取主数据、按规则随机组合，模拟的是「已经走到终态的一批业务数据」，并没有实现员工登录 → 填写 → 提交 → 真人审批 → 自动落账的真前台闭环。

## 十二、诚实边界：哪些做了、哪些是未来设计

这是卷五最该被记住的一张表。整卷所有「后续设计」都明确标注，绝不把讨论中的功能写成已上线：

尤其要拆清：H42～H46（自然语言→YAML、Contract 变更审批、Incident Copilot、NL2SQL、PII 分类）在卷五里是**单列的设计小节**，每条都写明「LLM 只生成草稿/只给建议/只解释，不能直接改生产规则、不能直接决定权限、不能把推测当事实」，并标注当前未实现。这和卷七（LLM 卷）里那些已经实证落地的 LLM 能力是两回事——卷五只是把设想讲清楚，卷七才把它们做成代码。

**闭环小结**：因为用户反复追问「登录在哪、审批在哪、LLM 能不能直接改规则」 → 所以卷五把这些明确拆成「未来 ERP 两个世界」：当前已实现的是右侧数据治理链路和模拟数据生成器，左侧真正的 ERP 登录/表单/真人审批属于未来设计 → 结果：读者不会被「系统看起来很完整」误导，能分清已实现与规划。

## 十三、这一卷在整条主线上的位置

把卷五放回整个 ERP 数据契约项目的演进里看：卷一到卷四是前序——本地 Parquet 原型、Data Contract 规则从 25 长到 55、Kestra 编排、PostgreSQL 迁移起步、Secret 与钉钉告警，解决的是「数据质量门禁 + 自动化 + 通知」。卷五补的是上游业务数据生产线，让「Contract 管数据」第一次有了真实的业务源头，而不是自己编的账。

它又为后续埋了清楚的接口：员工主数据、审批规则、业务申请这些表，正是卷六（ERP 业务前台）做登录与申请页面的基础，也是卷七（LLM 卷）里 Contract Copilot 解析「自然语言 → 结构化规则 → candidate YAML」所操作的同一套主数据和契约定义。主线一句话始终是：**Contract 管数据，Runtime 管 Contract 的持续执行，Governance 管 Contract 的变化，LLM 辅助 Governance 与运行诊断**——卷五把最前面的「数据从哪来、为什么可信」这件事钉死了。

整卷最终想让一个完全不了解项目的人顺着看下来自然形成：我原来有一个 Data Contract → 但它依赖静态数据 → 所以我补业务数据库 → 业务被拆成 6 张表 → 财务事实通过 View 暴露成契约接口 → 先用 12 条数据验证 → 再写生成器扩大到 10,022 条 → 正常数据先 PASS → 故意注入 5 类异常 → Contract FAIL → 恢复干净基线 → Pytest 建立自动回归 → Kestra 每天 06:00 自动执行 → 失败钉钉告警 → Streamlit 中文 Dashboard → 最终形成完整数据质量工程闭环 → 再讨论未来 ERP / RBAC / LLM Copilot。这才是本卷真正要传递的逻辑。
