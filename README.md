# ERP 数据契约治理平台 · 项目总仓

> **一句话**：面向采购、研发、销售等企业场景，构建从员工业务申请、审批流转、财务交易生成，到数据质量校验、自动化告警与 LLM 辅助契约治理的一体化 **ERP 数据契约模拟平台**。
>
> **主线**：**契约管数据，治理管契约变更，LLM 辅助治理与运行诊断。**
> 所有能力都围绕一个目标构建——**让 Data Contract 的检查变得更有意义**。

---

## 一、这个项目解决什么问题

数据质量工具（如 `datacontract-cli`）能跑出"72 项全部通过"，但这份结果对业务没有意义：

- **数据没有源头**——检查的是外部下载的数据集，不是业务系统真正产生的数据；
- **检查完了没人看**——结果躺在终端里，业务与财务人员读不懂；
- **规则改了没记录**——契约可以随时被改，谁改的、改了什么、影响哪些历史数据，没人说得清；
- **规则只能工程师写**——财务人员懂规则，但写不出 YAML。

本项目按"**先有需求，后有功能**"的原则逐块补齐：先做出能产生数据的业务系统，再让契约检查有对象；再让检查结果被人看见；再让契约变更被治理；最后才让 LLM 介入——**只让它做"理解人话"这一件事**，分类、编号、生成、比对、定位全部由确定性代码完成。

## 五、架构主线：LLM 只做它该做的事

```
财务人员一句话
      ↓  LLM（理解人话 → 结构化 JSON）
   两道闸：① Schema 校验  ② 字段白名单
      ↓  通过后才继续
   确定性 Python（分类 / 内容寻址生成 RULE_ID / 生成 YAML）
      ↓
   candidate YAML + diff  ──绝不覆盖生产契约──▶  变更单审批  ──▶  Git 提交作为技术证据
```

**四条硬护栏**（任何一条破了就不算 Copilot）：

1. 不直接写生产 YAML——产出物只有 `candidate` 与 `diff` 两个文件；
2. 不直接执行变更——必须走变更单；
3. 输出必过 Schema 校验；
4. 固定 `model` / `prompt` 版本且 `temperature=0`，保证语义回归可复现。

**规则 ID 走内容寻址**（`copilot_{signature}`），与 LLM 输出无关——同一条规则永远得到同一个 ID。

### 真模型取证得到的结论

用 DeepSeek 真模型跑取证，发现两个真实问题并已修正：

- **模型善数值边界、不善内控语义方向**："审批级别应 ≥ N"被写成"= N"。这不是靠推测，是实测出来的。
- **危险需求拒绝率 0/3**：提示词升级到 `rule-extract-v2` 后提升到 **2/2**。
- 沉淀为 **18 条 Evals 回归集**，离线回放写入 GitHub Actions 工作流作为合并前门禁。

## 六、契约变更治理

- **版本指针**：`from_version` / `to_version`，变更全程可追溯；
- **独立审批资格**：后端强制 `requested_by ≠ approved_by`，新增 `contract_approver` 角色，**资格只看角色、不绑定职级**；
- **Git 提交作为技术证据**回填变更单，配套防重复提交幂等；
- **三项治理能力**：
  - **③ 变更影响评估**：新旧契约各跑一份结果，按 `(transaction_id, rule_id)` 对齐做四分类（PASS→PASS / PASS→FAIL / FAIL→PASS / FAIL→FAIL），凡出现 PASS→FAIL 一律要求签字——回答"改完规则以后，以前那些数据怎么办"；
  - **④ 契约版本回退**：只移动版本指针，业务账一笔不动，且**回退本身也生成一条待审批变更单**；
  - **⑤ 事中临阈提示**：仅提示、绝不拦截。

## 七、LLM 运行诊断与修复闭环

- **失败先做确定性聚类**（按命中规则分类），LLM **只解释已确定的类别**；
- 缓存键 = `契约版本 + 规则 + 错误签名 + 提示词版本 + 模型版本`，**一类只解释一次**；
- 定位由**确定性 SQL** 完成（源表 / 责任人 / 字段）并生成结构化修复单，**LLM 不参与定位**；
- 重复告警用**进程内 Set/TTL** 去重（同执行、同规则、同时间窗口），不引入 Redis；
- **Incident Copilot**：把一次执行的失败批次与 Kestra 日志聚合为四节事故报告（已确认事实 / 异常证据 / 潜在原因 / 修复建议），`incident_id` 内容寻址保证幂等。

## 八、跨切面护栏

每次 LLM 抽取都写审计日志：

```
request_id / model / prompt_version / input_hash / 脱敏摘要 / output / timestamp / operator
```

可顺变更单追溯到人。使用外部模型时**前置 PII 脱敏**（邮箱 / 手机 / 身份证正则掩码），日志只记录结构化交接点，**不留存可还原的个人数据**。

## 九、快速复现

```bash
cd 8_项目产出合集_源码_PPT_讲稿_简历/02_项目源代码_data-contract-demo

# 1. 建库：执行 database/ 下的建表 SQL（PostgreSQL 中）
#    连接口令只从环境变量读取：DATACONTRACT_POSTGRES_PASSWORD 或 ERP_DB_PASSWORD

# 2. 生成仿真业务数据（10,022 笔）
python generate_demo_data.py

# 3. 跑契约检查（72 项）
datacontract test financial_data_contract.yaml

# 4. 回归测试
pytest -q

# 5. Evals 离线回放（CI 门禁）
python evals/run_evals.py
```

数据库连接口令**只从环境变量读取**（`DATACONTRACT_POSTGRES_PASSWORD` 或 `ERP_DB_PASSWORD`），代码中不存在任何硬编码口令。

> **关于 Kestra / Docker 编排**：`kestra/docker-compose.yml` **未纳入本仓库**——原工程将其视为独立运行时子项目排除在外，且该文件可能包含数据库连接口令，出于隐私考虑不做上传。
> 契约检查本身可直接用 `datacontract test` 运行，不依赖 Kestra；定时编排部分请参看卷三报告中的配置说明自行搭建。

## 十、诚实边界（重要）

本项目坚持区分「已实证」与「待触发条件」，**不把规划讲成已完成**。

**已实证**（有代码、有产物、有输出记录）：
72 项契约检查、Kestra 定时门禁、异常注入验证、Pytest 回归、Streamlit 看板、LLM Copilot 四护栏、Evals 18 条、失败解释与修复闭环、Incident Copilot、③④⑤ 三项治理、审计日志与 PII 脱敏。

**待触发条件**（尚未执行，非缺陷）：
- 三项治理能力在真实 PostgreSQL 环境上的实跑；
- Kestra execution API 真实取数（当前用本地日志）；
- GitHub Actions 在真实 runner 上的执行；
- 数据量扩展到千万级后的执行引擎升级（触发条件：单次检查超出 SLA）。

**明确不做**：NL2SQL、SQL Copilot、数据分类 Copilot（无需求来源，已移出主线）。
